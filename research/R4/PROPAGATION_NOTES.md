# R4 — PROPAGATION_NOTES

For each load-bearing fact: what breaks downstream if it is wrong or weakened. Read this before
re-using any R4 conclusion in the architecture freeze, the check registry, or the test fixtures.

| Fact | If it is wrong or weakened, re-check these |
|---|---|
| **R4-F01** (TCI probe status is a coarse aggregate) | Everything. If probe status were per-fact reliable, the "per-fact outcome" column in `TECHNOLOGY_INVENTORY.md` §0 would be redundant, but the reverse error is fatal: any downstream document that copies a probe's status as a fact's status inherits at least seven wrong classifications. Also invalidates the sensor design rule "capture outcome per observation, never per check". |
| **R4-F02** (`/etc/mdadm/mdadm.conf` exists) | `TECHNOLOGY_INVENTORY.md` §3 row; any RAID check keyed on config-file existence; the lead's confidence in `state/HOST_SNAPSHOT.json` prose generally — this is the only place the prose was found to contradict the evidence, and finding one suggests looking for others. |
| **R4-F03 / R4-F55** (NVMe identity is world-readable sysfs, 0444, no tool needed) | The machine-description storage path (contract B5/B5a); the claim that the sensor has no external-binary dependency for storage inventory; fixture design for `/sys/class/nvme`. If wrong, storage inventory needs `nvme`/`lsblk` and becomes UTILITY_MISSING-fragile. |
| **R4-F04 + R4-F54** (SMART is EACCES; remediation is CAP_SYS_ADMIN, not group `disk`) | The drive-health finding's `reason` text and any remediation the sensor prints. Getting this wrong puts a confidently wrong instruction in front of an operator. Also affects `STORAGE_ASSESSMENT.md` §1, Q14 and trap T-S4, and the strength of the storage-category argument (§4.1 item 2). |
| **R4-F05 + R4-F57 + R4-F58** (dm-crypt absent; SED unknown by construction; model string cannot decide it) | The encryption-at-rest check's scope statement, its severity, and whether it may be `fail` at all. If SED state turned out readable, the check upgrades from "fail for dm-crypt, unknown for SED" to a single definite answer — and `STORAGE_ASSESSMENT.md` Q2 and §4.1 item 1 both change. |
| **R4-F07** (no redundancy, provable) | The single strongest storage finding and therefore §4.1 items 1 and 5, the storage-category verdict, and the recommended check list in `HOST_SPECIFIC_PLAN.md` §E. |
| **R4-F08** (lsblk FSTYPE is udev-derived) | The wording of every "device has no filesystem" statement; trap T-S3; `OBSERVATION_REQUEST` R4-OR8. If the account could actually read the device, the claim strengthens from "no signature known to udev" to "no signature on disk" — and Q6/Q7 in the confidence table change character. |
| **R4-F09 + R4-F46** (BMC sysfs identity is readable, and the read reflects a live Get Device ID) | The entire BMC_INBAND_ACCESS design. F46 is the anchor: if the attributes were static/cached firmware data rather than driver-issued queries, the category's strongest check degrades from "the BMC answered" to "the driver claims a BMC", and `HOST_SPECIFIC_PLAN.md` §D2 must be rewritten. F46 is LIKELY (0.8), read from `master` rather than the v6.8 tag — worth re-verifying at the host's tag before the freeze. |
| **R4-F12** (mode bits are not authorisation; `/dev/kmsg` 0644 but EPERM) | Every "who can read X" check in SECRETS_ON_DISK and BMC_INBAND_ACCESS; the design rule that a policy gate (dmesg_restrict, ptrace_scope, perf_event_paranoid, lockdown) must appear in the evidence alongside the mode. |
| **R4-F13** (only `sudo` has members; `disk`, `adm`, `systemd-journal` are empty) | The "no unprivileged path exists" reasoning in the storage-health finding; the journal-unreadable finding; the BMC device-permission finding. This is the cross-check that turns several mode-based observations into proofs. If group data were incomplete (e.g. a directory backend), all three weaken — but `users.nsswitch` shows `files` only, which is the corroboration. |
| **R4-F14 + R4-F34** (kernel drift provable; the marker file's absence is not evidence) | The Update/Drift category's central check; `HOST_SPECIFIC_PLAN.md` §G. If the marker mechanism were guaranteed present, the check could be simpler — but it would then be wrong on hosts without `update-notifier-common`. |
| **R4-F15** (empty apt index makes "nothing upgradable" meaningless) | Any patch-currency check. This is the highest-value false-negative trap identified; if it were wrong, a `pass` on patch currency would be legitimate here, and the Update/Drift category becomes materially stronger as a custom-category candidate. |
| **R4-F16** (Secure Boot disabled + Setup Mode, two independent unprivileged paths) | The boot-chain category's severity argument and therefore `STORAGE_ASSESSMENT.md` §4.2 item 3 — the comparison that keeps the storage verdict honest. If efivarfs reads were unreliable, the boot-chain competitor weakens and storage looks relatively stronger. |
| **R4-F19 + R4-F20 + R4-F31** (sshd -T unusable; socket activation owns the listener; the generator question is contested) | The REMOTE_ACCESS parser design (contract C4a), including whether the sensor must implement Include/Match/first-wins semantics itself. If `sshd -T` were somehow usable unprivileged, most of that parser is unnecessary. F31 being contested means the sensor must read the effective socket configuration at runtime rather than assume either form. |
| **R4-F22 + R4-F33** (sudo policy unknown; cloud-init writes 90-cloud-init-users at 0440) | Any statement about what a compromised key grants; the BMC escalation-path discussion; the standing prohibition on running `sudo -l`. If the policy became readable, several unknowns in REMOTE_ACCESS become definite answers. |
| **R4-F23** (owner is not determinable) | The machine-description `owner` field (contract B2/B2a) and the NOTES.md ambiguity discussion. If a tenant identifier were found anywhere readable, the explicit-unknown design and the `owner_candidates` list would both change. |
| **R4-F27** (bounded finds produce bounded negatives) | Every SECRETS_ON_DISK finding's phrasing and evidence block; the requirement that scan scope (roots, depth, filesystems, skipped dirs, budget) is part of the evidence. If ignored, the sensor claims "no secrets" where it means "none found in the part I could see" — precisely the failure mode the brief calls critical. |
| **R4-F30 + R4-F49** (DMI entry directories traversable; attributes root-only at v6.8) | `HOST_SPECIFIC_PLAN.md` §D1 and the "distinguish no-BMC from driver-not-bound" technique in `GENERIC_FALLBACK_PLAN.md` §8. F49 corrects F30 and is itself CONTESTED pending R4-OR7; if the `type` attribute turned out readable, D1 gains a field-level claim. |
| **R4-F37** (`size` is in fixed 512-byte units) | Every reported `size_bytes` in the machine description. Wrong here means every capacity is wrong by a factor of 8 on 4Kn devices — and correct on this host, so the bug would ship undetected. Fixtures must include a 4Kn device. |
| **R4-F38** (containers see the host's `/sys/block` and DMI) | The entire genericity story. If sysfs were namespaced, the container column in `GENERIC_FALLBACK_PLAN.md` §2 and §4 collapses to "nothing visible", which is the *safe* failure; the dangerous direction is the one established here, where a containerised run silently reports the host's hardware as its own. Any execution-context gating in the sensor depends on this. |
| **R4-F44** (`apparmor/profiles` is 0444) | Whether R4-OR4 is answerable in one read, and whether an LSM check can claim enforcement. If the file were root-only, AppArmor enforcement is unknown by construction rather than merely unobserved. |
| **R4-F59** (`write_cache` says nothing about power-loss protection) | The severity and wording of the write-cache observation. If treated as a durability claim it becomes a false statement about the hardware. |
| **R4-F60** (the exact "no arrays" mdstat signature) | Trap T-S2 and the redundancy check's implementation. A check keyed on the Personalities line alone produces a false positive on every host with RAID personalities loaded — which is most Ubuntu hosts. |

## Cross-cutting dependencies

- **If the lead chooses boot chain over storage as the custom category** (`STORAGE_ASSESSMENT.md` §4.3),
  then R4-F16, F17, F25 and the §F block of `HOST_SPECIFIC_PLAN.md` become load-bearing, and R4-F05/F07/F58
  drop to supporting evidence inside the required categories.
- **If `finding.schema.json` forbids additional properties** (contract AM-7), the scope/boundedness metadata
  that R4-F27 requires must move inside `evidence`, and every plan row that says "the evidence must carry
  its scope" needs re-siting, not re-deciding.
- **If any OBSERVATION_REQUEST is answered**, the labelled assumption beside it in `OBSERVATION_REQUESTS.md`
  must be replaced with the observation, and the corresponding row above re-read. R4-OR4 and R4-OR7 are the
  two most likely to change a recommendation; R4-OR5 is the one most likely to stay unknown permanently.
