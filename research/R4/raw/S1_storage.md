## Q1 — NVMe sysfs ABI on Linux 6.8

**First finding: there is no `Documentation/ABI/{stable,testing}/sysfs-class-nvme` file in the v6.8 tree.** Verified by directory listing:
```
curl https://git.kernel.org/.../tree/Documentation/ABI/stable/?h=v6.8   -> sysfs-block present, no sysfs-class-nvme, no sysfs-nvme*
curl https://git.kernel.org/.../tree/Documentation/ABI/testing/?h=v6.8  -> only sysfs-nvmem-cells (nvmem, unrelated), no sysfs-class-nvme
```
So the only authoritative ground truth for NVMe controller/subsystem sysfs attribute existence and permission is the driver source, `drivers/nvme/host/sysfs.c` (v6.8), which I fetched and read directly:
`https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/nvme/host/sysfs.c?h=v6.8`

Controller device attrs (`/sys/class/nvme/nvmeX/...`, backed by `nvme_dev_attrs[]`, attached via `device_add_disk`-style `nvme_dev_attr_groups`, flat — no subdirectory):
- `model`, `serial`, `firmware_rev` — via `nvme_show_str_function()` macro → `static DEVICE_ATTR(field, S_IRUGO, field##_show, NULL)` → **mode 0444, world-readable**. Source string comes from `ctrl->subsys->field` (cached from Identify Controller at attach time — the driver already did the privileged Identify once at probe; userspace just reads the cached copy, no ioctl/capability needed).
- `cntlid`, `numa_node`, `queue_count`, `sqsize`, `kato` — via `nvme_show_int_function()` → same `S_IRUGO` (0444).
- `transport`, `state`, `subsysnqn` — explicit `static DEVICE_ATTR(transport, S_IRUGO, ...)`, `DEVICE_ATTR(state, S_IRUGO, ...)`, `DEVICE_ATTR(subsysnqn, S_IRUGO, ...)` — **0444**.
- `cntrltype`, `dctype` — `DEVICE_ATTR_RO(cntrltype)`, `DEVICE_ATTR_RO(dctype)` — 0444 (macro expands to S_IRUGO too).
- `hostnqn`, `hostid`, `ctrl_loss_tmo`, `reconnect_delay`, `fast_io_fail_tmo`, `address` — attrs exist in the array but `nvme_dev_attrs_are_visible()` **hides** `hostnqn`/`hostid`/`ctrl_loss_tmo`/`reconnect_delay`/`fast_io_fail_tmo` whenever `!ctrl->opts` (i.e. `ctrl->opts` is only set for NVMe-oF fabrics transports built via `nvmf`); `address` is hidden if the transport ops don't implement `get_address`. **On the Lava host (local PCIe NVMe, not fabrics) these files will not exist at all** — this is a fact worth encoding as "absence expected, not evidence of anything."
- `reset_controller`, `rescan_controller`, `delete_controller` — write-only (`S_IWUSR`), root-only by mode; irrelevant to a read-only sensor and correctly out of scope.

Subsystem attrs (`/sys/class/nvme-subsystem/nvme-subsysX/...`, `nvme_subsys_attrs[]`, `SUBSYS_ATTR_RO(..., S_IRUGO, ...)`): `model`, `serial`, `firmware_rev`, `subsysnqn`, `subsystype` — all **0444**. `iopolicy` only under `CONFIG_NVME_MULTIPATH`.

Namespace-level attrs (this is the part the question calls `/sys/block/nvmeXnY/nvme/*` — **that path is wrong**; verified from source there is no `nvme/` subdirectory. `nvme_ns_attr_groups` is passed straight into `device_add_disk(ctrl->device, ns->disk, nvme_ns_attr_groups)`, and the `attribute_group` struct has no `.name`, so the files land flat at **`/sys/block/nvmeXnY/{wwid,nguid,uuid,eui,nsid,csi,metadata_bytes,nuse}`** directly, not nested):
- `wwid`, `nguid`, `uuid`, `eui`, `nsid`, `csi`, `metadata_bytes` — `DEVICE_ATTR_RO(...)` → 0444, visibility gated only on whether the identifier type is non-zero for that namespace (`nvme_ns_attrs_are_visible`), not on privilege.
- `nuse` — 0444, namespace utilization in logical blocks (requires an internal cached Identify Namespace; still just a sysfs read for userspace).

`/sys/block/nvmeXnY/queue/*` is **generic block-layer**, not NVMe-specific — covered in Q3 from `Documentation/ABI/stable/sysfs-block` (the one ABI doc file that *does* exist and is current).

`/sys/class/nvme-subsystem/` itself: a class directory; existence is what tells you the running kernel's nvme-core registered ≥1 subsystem; readable/traversable unprivileged (standard sysfs class dir permissions, 0755).

Design impact: every one of these controller/subsystem/namespace identity+state attributes is **world-readable by kernel design** (`S_IRUGO`/`DEVICE_ATTR_RO`), independent of the char-device permission story in Q2. A read-only unprivileged sensor can fully enumerate model/serial/firmware/state/transport/subsysnqn/cntlid/numa_node/wwid/nguid/uuid/nsid/nuse with zero ioctl calls and zero privilege. Do not expect `hostnqn`/`hostid`/`address` to exist on a local PCIe host — their absence is expected-and-correct, not UNKNOWN.

Source: drivers/nvme/host/sysfs.c @ v6.8 (primary, read directly), lines with `nvme_show_str_function`/`nvme_show_int_function`/`nvme_dev_attrs[]`/`nvme_ns_attrs[]`/`nvme_subsys_attrs[]`.

## Q2 — nvme-cli subcommands: sysfs read vs ioctl, exact unprivileged failure mode

Verified from `drivers/nvme/host/ioctl.c` @ v6.8 (`https://git.kernel.org/.../plain/drivers/nvme/host/ioctl.c?h=v6.8`):

- `nvme_dev_ioctl()` (the char-device `/dev/nvmeX` ioctl entry point) dispatches `NVME_IOCTL_ADMIN_CMD` / `NVME_IOCTL_ADMIN64_CMD` straight into `nvme_user_cmd()`/`nvme_user_cmd64()`, which call `nvme_cmd_allowed(ns=NULL, cmd, ...)`.
- `nvme_cmd_allowed()` logic (function body read directly, lines ~16-85):
  - vendor-specific opcodes or Fabrics command → always `admin:` (needs `CAP_SYS_ADMIN`).
  - `ns == NULL` (i.e. controller-wide command on `/dev/nvmeX`, which is what `id-ctrl`/`smart-log` use) and opcode is `nvme_admin_identify`: **only** allowed unprivileged if CNS ∈ {`NVME_ID_CNS_NS`, `NVME_ID_CNS_CS_NS`, `NVME_ID_CNS_NS_CS_INDEP`, `NVME_ID_CNS_CS_CTRL`, `NVME_ID_CNS_CTRL`}. Any other admin opcode (including `nvme_admin_get_log_page`, which is what `smart-log` uses) → `goto admin` → requires `capable(CAP_SYS_ADMIN)`.
  - So **`nvme smart-log` always needs CAP_SYS_ADMIN** (Get Log Page is never in the unprivileged allow-list). **`nvme id-ctrl` uses Identify with CNS=Controller, which the kernel *would* allow unprivileged** — IF the process can even open `/dev/nvme0` in the first place.
  - Historical note (do not confuse with the shipped behavior): an RFC from Logan Gunthorpe (Oct 2021, LKML `https://lkml.iu.edu/hypermail/linux/kernel/2110.0/00967.html`) proposed also whitelisting `get_log_page` unprivileged; **that proposal, as posted, is not what's in v6.8** — the merged `nvme_cmd_allowed()` only whitelists a subset of Identify CNS values, not Get Log Page. Confirmed by reading the actual v6.8 source, not the patch mail.
- Char-device permission is the earlier gate: `open("/dev/nvme0")` must succeed first. Confirmed via `systemd/systemd` issue #26009 (`https://github.com/systemd/systemd/issues/26009`, secondary but directly-quoted `ls -l` output from a systemd maintainer bug report): `/dev/nvme0` is `crw------- root root` (**0600, not even group `disk`**), while `/dev/nvme0n1*` block devices are `brw-rw---- root disk` (0660). Root cause per that issue: `50-udev-default.rules` assigns `GROUP="disk"` to `SUBSYSTEM=="block"` devices, but the controller node is a **char** device and doesn't match that rule, so it keeps the kernel/devtmpfs default of root:root 0600.
- **Practical consequence for the Lava host** (uid 1000, groups `ubuntu`,`sudo`, not `disk`): `open("/dev/nvme0", O_RDONLY)` fails with `EACCES` *before* any ioctl/capability check is reached — this is why **both** `nvme smart-log` and `nvme id-ctrl` were observed to return "Permission denied" on the host, even though `id-ctrl`'s specific Identify CNS is one the kernel ioctl layer would otherwise allow unprivileged. Being in group `disk` would not have been sufficient for the char device either way (the group bit doesn't apply to `/dev/nvme0`), only root, or a user granted `CAP_SYS_ADMIN`, or a custom udev rule relaxing the char device's mode.
- `nvme-cli`'s error text/exit code: the exact string reported in the field for `smart-log` under this failure class is `"smart log: Permission denied"` (quoted from an LKML RFC thread body describing the exact problem, `https://lkml.iu.edu/hypermail/linux/kernel/2110.0/00967.html`, secondary but a firsthand nvme-cli/kernel developer's own characterization). I could **not** independently confirm the precise nvme-cli-version-specific exit code (nvme-cli generally returns non-zero, commonly 1, on any command failure) from primary nvme-cli source — GitHub raw fetches were rate-limited/404'd during this session (repo layout changed; top-level `nvme.c` path used in old clones no longer resolves at `master`). **Marking exit-code precision as NOT CONFIRMED** — do not hardcode an exact byte-for-byte value in the sensor without a real repro on the host (which the recon plan already captured: "returned Permission denied").
- `nvme list` / `nvme list-subsys`: confirmed (via WebSearch summarizing nvme-cli docs/behavior, secondary — GitHub source fetch was rate-limited this session) that these enumerate via `/sys/class/nvme/nvmeX/**` (sysfs scan), not ioctl — consistent with Q1's finding that identity attributes are 0444. This means **`nvme list` should succeed unprivileged** even when `smart-log`/`id-ctrl` fail — worth confirming empirically on the host if not already done, since it's a strictly-better fallback path than raw sysfs walking for enumeration (though the sensor should read sysfs directly rather than shell out, per the "stdlib → native primitive" design rule).

Design impact: **do not shell out to `nvme-cli` for identity/state facts** — read `/sys/class/nvme/*` directly (Q1), it's strictly more available (no exec dependency, no permission surprise) than the CLI. Only SMART/health-log data (temperature, wear, media errors, power-on hours) is genuinely locked behind CAP_SYS_ADMIN with no unprivileged sysfs equivalent — that must be reported `unknown` with reason "requires CAP_SYS_ADMIN via NVME_IOCTL_ADMIN_CMD (Get Log Page), char device is root:root 0600" rather than treated as a missing-utility problem.

## Q3 — Block-layer queue attribute semantics

All confirmed from `Documentation/ABI/stable/sysfs-block` @ v6.8 (fetched directly, this file **does** exist and is current/authoritative — 737 lines, one `What:`/`Description:` block per attribute):
`https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/Documentation/ABI/stable/sysfs-block?h=v6.8`

- `queue/write_cache` — **[RW]**. Exact text: *"When read, this file will display whether the device has write back caching enabled or not. It will return 'write back' for the former case, and 'write through' for the latter. Writing to this file can change the kernels view of the device, but it doesn't alter the device state. This means that it might not be safe to toggle the setting from 'write back' to 'write through', since that will also eliminate cache flushes issued by the kernel."* — **This document says nothing whatsoever about power-loss protection.** It is purely "does the block layer currently believe write completions can be cached and need explicit FLUSH/FUA, yes/no." A drive can report `"write through"` (as the Micron 7450 PRO does on the Lava host) for reasons entirely orthogonal to whether it has capacitor-backed PLP — e.g. NVMe write-cache reporting (VWC bit in Identify Controller) being off/disabled by firmware default, or the volatile write cache being administratively disabled, while the drive's *non-volatile* PLP-protected buffer (a separate hardware feature) still exists and is unaffected by this Linux-visible flag. **"write through" here is NOT evidence of "no PLP"** — the sensor must not conflate the two. The only way to learn about the device's own non-volatile-cache/PLP hardware feature is the NVMe Identify Controller VWC field or vendor datasheet (Q8), not this sysfs file.
- `queue/rotational` — [RW], *"used to stat if the device is of rotational type or non-rotational type."* Present and writable (i.e., it's advisory metadata block-layer keeps, not device-verified truth) — for NVMe it will be `0` and there's no ioctl needed to read it.
- `queue/scheduler` — [RW], shows current + available I/O schedulers, active one in `[brackets]`. Matches host fact "scheduler none" — meaning the current elevator is literally the `none` (no-op) scheduler, appropriate/expected for NVMe with a fast, deep hardware queue.
- `queue/discard_granularity` — [RO], *"the size of the internal allocation unit in bytes if reported by the device. Otherwise ... set to match the device's physical block size. A discard_granularity of 0 means the device does not support discard."* Host reports 512 (matches logical block size, not the 4096 physical size — some devices report granularity independent of physical block size).
- `queue/discard_max_bytes` — **[RW]**, *software* limit (Linux-imposed, can be lowered by admin to fight latency spikes), distinct from `discard_max_hw_bytes` [RO] which is the *hardware* limit reported by the device driver.
- `queue/logical_block_size` [RO] *"smallest unit the storage device can address... typically 512 bytes"*; `queue/physical_block_size` [RO] *"smallest unit a physical storage device can write atomically... usually the same as logical block size but may be bigger... For stacked block devices ... contains the maximum physical_block_size of the component devices."* Matches host: logical 512 / physical 4096 (512e drive).
- `queue/nr_zones` [RO] — zoned-device attribute; *"For regular block devices, the value is always 0."* Confirms this attribute existing/being 0 is expected and uninformative for a conventional (non-ZNS) NVMe drive like the 7450 PRO — its presence isn't evidence of zoned support, its value (0) is what proves non-zoned.

Design impact: treat `write_cache` strictly as "does the OS currently need to issue FLUSH/FUA for this device's volatile cache," never as a PLP/data-durability claim. If the sensor wants to report on PLP it must either (a) explicitly say UNKNOWN because PLP requires privileged Identify Controller data or a vendor datasheet lookup keyed off model string, or (b) hardcode a note derived from the vendor datasheet for the exact model matched (fragile, and the model-string ambiguity in Q8 undermines even that).

## Q4 — Encryption-at-rest markers, unprivileged

### dm-crypt / LUKS
Primary source: cryptsetup's own `lib/libdevmapper.c` (fetched directly from the project's own GitLab, `https://gitlab.com/cryptsetup/cryptsetup/-/raw/main/lib/libdevmapper.c`), function `dm_prepare_uuid()`, with the format spelled out in a code comment:
```
/*
 * UUID has format: CRYPT-<devicetype>-[<uuid>-]<device name>
 * CRYPT-PLAIN-name
 * CRYPT-LUKS1-00000000000000000000000000000000-name
 * CRYPT-TEMP-name
 */
```
- Confirmed prefix constant is `DM_UUID_PREFIX` (= `"CRYPT-"`) followed by `<type>-<uuid-without-dashes>-<name>`. Types observed in cryptsetup's own vocabulary include `PLAIN`, `LUKS1`, `TEMP`; **LUKS2** volumes use type token `LUKS2` (cryptsetup passes the format-version string as the `type` argument to `dm_prepare_uuid()` when activating — I confirmed the *mechanism* from source but did **not** find a literal `"CRYPT-LUKS2-"` string constant in this file; it's produced dynamically from `crypt_get_type(cd)`, not a hardcoded string, so grep for the literal string is the wrong test). **Practical rule for the sensor: on a device-mapper LUKS volume, `/sys/block/dm-N/dm/uuid` will read as `CRYPT-LUKS1-<32hex>-<name>` or `CRYPT-LUKS2-<32hex>-<name>`; match on the `CRYPT-LUKS` prefix (covers both versions), not an exact string.** `/sys/block/dm-N/dm/name` gives the human-assigned mapping name (e.g. what `dmsetup ls` would show). Both files are plain sysfs text files under a directory that is part of the standard device-mapper kernel ABI (kobject attrs, world-readable — device-mapper does not gate `dm/uuid`/`dm/name` behind CAP_SYS_ADMIN, they're informational).
- **On the Lava host: no `/dev/mapper/*` devices exist except `control`, so this whole class of markers correctly resolves to "no dm-crypt/LUKS present" — provable, not just unknown**, because a full listing of `/sys/class/block/dm-*` (or `/dev/mapper/*` beyond the always-present `control` node) is achievable unprivileged and its absence is a positive, listable result per the project's "absence is only provable from a successful listing" rule.
- `lsblk -o NAME,TYPE,FSTYPE` showing `crypto_LUKS` as FSTYPE for an *unopened* LUKS-formatted partition — this is the blkid/udev-derived filesystem signature the LUKS header itself advertises (LUKS partitions carry a small superblock blkid recognizes directly as a "filesystem" type of `crypto_LUKS`, before any `cryptsetup open`/dm node exists at all), and per Q6 findings, `lsblk` gets this from the udev db without needing raw device read access. This is actually the more useful "is there an unopened encrypted volume sitting on disk" signal for an unprivileged sensor than dm/uuid.
- `/proc/crypto` — world-readable (standard procfs listing of registered kernel crypto API algorithms/ciphers); tells you which crypto primitives the *kernel* has loaded (e.g. `aes`, `xts(aes)`), **not** whether any block device is actually using them. Weak/indirect signal only — a machine can have `xts(aes)` loaded because it's built into the kernel image or loaded for unrelated reasons (e.g. dm-crypt module autoload, WireGuard, fscrypt), independent of any encrypted volume existing.
- `/etc/crypttab` — regular file, mode typically 0644 root:root (no secrets in it, just device+keyfile+options references), readable unprivileged on most distros; absence or empty of non-comment lines is a genuine "no LUKS auto-unlock configured" signal, though a LUKS volume could still exist and be manually opened without a crypttab entry, so this is corroborating evidence, not proof of absence.

### NVMe TCG Opal / SED
Primary source: `block/sed-opal.c` @ v6.8 (fetched directly), function `sed_ioctl()`:
```
int sed_ioctl(struct opal_dev *dev, unsigned int cmd, void __user *arg)
{
	...
	if (!capable(CAP_SYS_ADMIN))
		return -EACCES;
	switch (cmd) {
	case IOC_OPAL_SAVE: ... case IOC_OPAL_LOCK_UNLOCK: ... /* all IOC_OPAL_* */
```
Every single `IOC_OPAL_*` operation is gated behind `CAP_SYS_ADMIN` at entry, uniformly, with **no exception for read-only/status queries**. I also grepped the whole file for `sysfs` — **zero matches**. **There is no sysfs file anywhere in the mainline kernel exposing OPAL locking/ownership state.** The only way to learn OPAL/SED status is the `IOC_OPAL_*` ioctl interface (root-only) or an NVMe Identify Controller OACS bit (also only reachable via the CAP_SYS_ADMIN-gated Identify/passthrough path for the OACS field specifically — Identify Controller *is* in the Q2 unprivileged-allowed CNS list, but that only helps if `/dev/nvme0` can be opened at all, which on this host it cannot, group `disk` or not). **Conclusion: OPAL/SED capability and lock state are 100% UNKNOWN to an unprivileged sensor on this host, full stop — not a partial signal, not inferable from any sysfs path.** The only thing available is the vendor part number (Q8), and even that is ambiguous (base part number is shared between SED and non-SED SKUs; see Q8).

### fscrypt (ext4 encryption)
Primary source: `fs/ext4/sysfs.c` @ v6.8 (fetched directly): a **global**, kernel-build-level feature flag directory exists at `/sys/fs/ext4/features/encryption` (along with `casefold`, `verity`, `metadata_csum_seed`, `fast_commit`, `encrypted_casefold`, etc.), all `EXT4_ATTR_FEATURE(name)` → mode 0444, attached under `ext4_root` kobject with subdir name `"features"` (confirmed at the `kobject_create_and_add(..., ext4_root, "features")` call). **This tells you the running kernel binary was built with `CONFIG_FS_ENCRYPTION`, i.e. ext4 encryption *support exists* — it does NOT tell you whether the specific mounted filesystem/superblock actually has the `encrypt` incompat feature bit set, nor whether any directory on it is actually encrypted.** There is no per-mount, per-superblock sysfs attribute for "this fs has encryption in use" that I could find in `sysfs.c`'s per-device attribute list (`s_es->s_feature_incompat` is exposed generically for other things but I did not find an `encrypt`-bit-specific per-mount RO attribute). To determine per-mount fscrypt usage unprivileged you would need `lsattr` on individual files/dirs (reports the encrypt flag per-inode if you can stat/lsattr it) — not a single global-truth check. Design impact: report ext4-encryption-build-support (global, cheap, unprivileged) separately from and never conflated with "this filesystem instance uses fscrypt" (which is effectively UNKNOWN without deeper per-inode probing the sensor likely won't do).

## Q5 — RAID/redundancy detection, unprivileged

Primary source: `drivers/md/md.c` @ v6.8 (fetched directly, 4916+ lines read via targeted greps).

- **`/proc/mdstat` registration**: `proc_create("mdstat", S_IRUGO, NULL, &mdstat_proc_ops);` — confirmed **world-readable (0444)**, no privilege needed to `cat` it, ever.
- **Exact "modules loaded, zero arrays" behavior**, read directly from `md_seq_show()`:
  ```c
  if (v == &all_mddevs) {
      status_personalities(seq);
      if (list_empty(&all_mddevs))
          status_unused(seq);
      return 0;
  }
  ```
  This proves: with the `md` core and ≥1 personality module (e.g. `raid1.ko`) loaded but **no arrays assembled**, the file's *entire* content is exactly:
  ```
  Personalities : [raid1]
  unused devices: <none>
  ```
  — i.e., a non-empty, populated `Personalities :` line is compatible with zero arrays existing; the only line that proves "no arrays" is the absence of any `md<N> : ...` block plus the presence of `unused devices: <none>`. If the `md` driver isn't loaded/compiled in at all, `/proc/mdstat` doesn't exist. **This is the key disambiguator the sensor needs: "no md arrays" is proven by (file exists, no per-array lines, `unused devices: <none>`), not by "Personalities" being empty** (personalities list only reflects which RAID-level kernel modules happen to be loaded, often true by default on Ubuntu even with zero arrays, since `mdadm`/initramfs commonly autoloads raid456/raid1 etc.).
  Historical/secondary corroboration of the general `/proc/mdstat` line format (unused-devices marker, personalities, per-array status like `[5/5] [UUUUU]`) from the kernel RAID wiki (marked "archived/obsolete" by the wiki itself, but format hasn't changed): `https://raid.wiki.kernel.org/index.php/Mdstat`.
- **`/sys/block/md*/md/{level,degraded,sync_action}`** — confirmed readable unprivileged directly from source: `md_level` is `__ATTR(level, S_IRUGO|S_IWUSR, level_show, level_store)` (readable by all, writable by owner/root only); `md_degraded` is `__ATTR_RO(degraded)` (0444 by the standard `__ATTR_RO` macro convention); `md_last_scan_mode`/`last_sync_action` likewise `__ATTR_RO`. **On this host these paths don't exist at all** (no `/dev/md*`), which — combined with `/proc/mdstat` showing no array lines — is a positive, doubly-corroborated "no md/RAID redundancy" result, not a guess.
- **`mdadm --detail /dev/mdX`** — requires the array to exist first (moot here); more importantly it typically needs to open the block device, which for an existing array would usually be readable via the `disk` group on the `/dev/mdX` block device (block devices get `GROUP=disk` per the same `50-udev-default.rules` rule discussed in Q2) — but since there are no arrays on this host this is moot; not independently re-verified with a source citation this session (lower confidence item, flagged).
- **LVM** — `/sys/block/dm-*` won't exist either (no dm devices beyond `control`). For general LVM detection semantics: dm-mapper UUIDs for LVM2 logical volumes use an **`LVM-` prefix** followed by an opaque VG-ID+LV-ID string (e.g. `LVM-9xxykCVg0xKc44BIJBS8e99AN5YLC3B9q5M2eqwrpkctW65g0vXkWz5Kf0WD72em`) — this is a **secondary-source-only** confirmation this session (WebSearch summary of community documentation, not the lvm2 source itself — I did not get to fetch lvm2's own source for the literal prefix constant before session scope ran long; mark **LIKELY not VERIFIED**).
- **Hardware RAID controllers via `lspci`**: `PCI_CLASS_STORAGE_RAID` = **0x0104**, confirmed directly from kernel's own `include/linux/pci_ids.h` @ v6.8 (primary source, exact `#define`). `lspci -d ::0104` or grepping class `0104` in `lspci -n` output is a legitimate unprivileged way to detect a discrete hardware RAID HBA (PCI config space class codes are readable by any user via sysfs `/sys/bus/pci/devices/*/class`, no root needed — `lspci` itself only needs root for *some* extended/vendor-specific capability decode, not for basic class-code enumeration). **On the Lava host this correctly should show no RAID-class PCI function** (it's bare-metal Micron NVMe direct-attach, no HBA) — again a provable absence via successful listing, not a guess.
- **`/sys/class/scsi_host`** — standard sysfs class directory, world-readable/traversable; existence of scsi_host entries here is orthogonal to NVMe (NVMe doesn't register as a scsi_host in the modern nvme-core driver) — not independently deep-dived this session; likely irrelevant to this specific host's storage stack (no SCSI/SATA/SAS HBAs reported in host facts).

Design impact: "no redundancy" is provable to a high confidence bar here via **three independent, all-unprivileged corroborating checks**: (1) `/proc/mdstat` has no array lines, (2) no `/sys/block/md*` or `/dev/md*` nodes, (3) no PCI class-0104 device. Any one alone is decent; all three together is about as close to a proof of absence as an unprivileged read-only sensor can get without root.

## Q6 — Filesystem/mount posture, unprivileged

- **`/proc/self/mountinfo` vs `/proc/mounts` vs `findmnt`**: `mountinfo` documented in `Documentation/filesystems/proc.rst` @ v6.8 (fetched directly, section 3.5), exact field layout:
  ```
  36 35 98:0 /mnt1 /mnt2 rw,noatime master:1 - ext3 /dev/root rw,errors=continue
  (1)(2)(3)   (4)   (5)      (6)     (n…m) (m+1)(m+2) (m+3)         (m+4)
  ```
  fields: (1) mount ID, (2) parent ID, (3) major:minor (`st_dev` for files on this fs), (4) root-within-fs, (5) mountpoint, (6) per-mount options, (n…m) optional tags (`shared:X`, `master:X`, `propagate_from:X`, `unbindable`), (m+1) `-` separator, (m+2) filesystem type (`type[.subtype]`), (m+3) mount source, (m+4) super (per-superblock) options. This is strictly richer than `/proc/mounts` (which only gives the classic `mnt_fsname mnt_dir mnt_type mnt_opts freq passno`-style single options string, no mount-ID/parent-ID/propagation/shared-subtree info, and — critically — collapses per-mount vs per-superblock options into one merged string, hiding e.g. per-bind-mount option overrides). `findmnt` is just a formatting/query layer over the same kernel data (it reads `/proc/self/mountinfo` itself). **For a sensor, `mountinfo` is the right source of truth** — world-readable (`/proc/self/mountinfo` and `/proc/<pid>/mountinfo` for your own pid are always readable by you), no privilege needed. Matches host fact `nvme0n1p2 ext4 / rw,relatime,errors=remount-ro` — that string is a mountinfo/mounts-style options field.
- **ext4 sysfs per-device stats**: confirmed directly from `fs/ext4/sysfs.c` @ v6.8: `errors_count` (`EXT4_RO_ATTR_ES_UI(errors_count, s_error_count)`, mode 0444 per the `EXT4_ATTR_OFFSET(... 0444 ...)` convention that macro expands through, reads `s_error_count` straight from the on-disk/in-memory superblock struct) — this is a running counter of filesystem errors ext4 itself has detected since the fs was created, exposed live without needing `dmesg`/root. `first_error_time`/`last_error_time` — also `EXT4_ATTR(..., 0444, ...)`. `lifetime_write_kbytes`/`session_write_kbytes` — also confirmed 0444 in source, and independently documented in `Documentation/ABI/testing/sysfs-fs-ext4` @ v6.8 (which *does* exist, unlike the NVMe one) as *"read-only ... shows the number of kilobytes of data that have been written to this filesystem since it was created"* (lifetime) / *"since it was mounted"* (session). Matches host fact `/sys/fs/ext4/nvme0n1p2/errors_count readable`.
- **Detecting network filesystems from mountinfo fstype**: purely a matter of matching the (m+2) filesystem-type field against known network fs type strings — `nfs`, `nfs4`, `cifs`, `smb3`, `ceph`, `9p`, `afs`, `glusterfs` (usually surfaces as a FUSE mount, so type will actually read `fuse.glusterfs`), `fuse.sshfs`, etc. This is a naming-convention/enumeration exercise, not something with a single kernel doc to cite — **no additional primary source found or needed**; it's inherent to how each filesystem registers its `file_system_type.name`. Caveat worth recording: FUSE-based network filesystems (glusterfs, sshfs, s3fs) will show up with an `fuse.<name>` prefix in the type field, so a naive `type == "nfs"` style match must also check for the `fuse.` prefix pattern to catch that whole class, or it will under-report.
- **Unmounted-but-present filesystem signature detection, unprivileged, and the udev-db path**: confirmed from man pages read directly (`man7.org`, mirrors upstream util-linux docs — treated as primary for util-linux tool semantics):
  - `lsblk(8)`: *"The lsblk command reads the sysfs filesystem and udev db to gather information. If the udev db is not available or lsblk is compiled without udev support, then it tries to read LABELs, UUIDs and filesystem types from the block device. In this case root permissions are necessary."* — i.e. **`lsblk -f` (FSTYPE) works fully unprivileged as long as udev has already probed the device and populated its database** (true by default on any systemd/udev-managed system at boot — udev runs `blkid`-equivalent probing as root during device coldplug/hotplug and caches the result); the sensor never needs to open the raw block device itself for this. The underlying mechanism (well-established, not separately re-derived from source this session) is that udev persists per-device properties keyed by devnum at `/run/udev/data/b<major>:<minor>` (tmpfs, root-owned but historically **world-readable** — this is standard udev behavior, not gated to root/disk — `lsblk`/`libblkid`'s udev backend reads this file directly instead of opening the block device node).
  - `blkid(8)`: *"lsblk(8) provides more information ... it does not require root permissions to get actual information. blkid reads information directly from devices and for unprivileged users it returns cached unverified information."* — confirms the same asymmetry from the other tool's own man page: **prefer `lsblk`/sysfs+udev-db reads over `blkid`** for an unprivileged sensor; `blkid` run as a non-root, non-`disk`-group user falls back to its on-disk cache (`/etc/blkid/blkid.tab` or similar) which may be stale/absent and is explicitly called out by upstream as "unverified."
  - **Design impact**: on this host (user not in `disk`, so direct open of `/dev/nvme1n1` — the unpartitioned, no-fs second drive — would fail) the sensor should read `/run/udev/data/b<maj>:<min>` and/or shell `lsblk -o NAME,FSTYPE,TYPE` (which itself consults the same udev db) rather than attempt to open the raw device or run `blkid` directly. This is exactly how "nvme1n1 has no partitions/fs" was presumably already established without root.

## Q7 — fstrim/discard privilege and semantics

- Confirmed directly from `fs/ext4/ioctl.c` @ v6.8: the `FITRIM` ioctl case explicitly checks `if (!capable(CAP_SYS_ADMIN)) return -EPERM;` before doing anything else (note: **`-EPERM`, not `-EACCES`** — worth getting right if the sensor ever tries to characterize the specific errno). So **`fstrim` (and thus `fstrim.timer`'s underlying unit, `fstrim.service`, which invokes `fstrim --fstab --verbose` and needs `CAP_SYS_ADMIN`) genuinely and unavoidably needs root/CAP_SYS_ADMIN to actually perform a trim** — this is filesystem-ioctl-level enforcement, not just "the systemd unit happens to run as root," so there's no unprivileged workaround.
- What **can** be read unprivileged: the *systemd unit's state* — `systemctl status fstrim.timer` / `systemctl is-enabled fstrim.timer` / `systemctl is-active fstrim.timer` are pure D-Bus/unit-file queries that any local user can perform without a privileged action or polkit prompt (only unit *management* verbs like start/stop/enable trigger the `org.freedesktop.systemd1.manage-units` polkit action) — confirmed via general WebSearch synthesis of systemd/polkit behavior this session (**secondary, not a directly-fetched systemd doc page — treat as LIKELY not VERIFIED-primary**, though this is extremely well-established systemd behavior). This tells you *whether the timer is scheduled to ever run*, not whether it has actually discarded anything recently (there's no "last successful trim timestamp" exposed anywhere unprivileged that I found).
- `queue/discard_granularity != 0` (Q3) is the correct unprivileged proof that the underlying block device *supports* discard at all (0 = "device does not support discard functionality" per the ABI doc text) — independent of whether `fstrim.timer` is enabled/has ever run. `queue/discard_max_bytes` (Q3) being non-zero and equal-or-related to `discard_max_hw_bytes` tells you the currently effective per-request discard size ceiling. Both are plain unprivileged sysfs reads.
- Host facts given (discard granularity 512) are consistent with an NVMe device that supports Dataset Management/TRIM at the same granularity as its logical block size.
