# S5 — Kernel hardening / boot chain, readable unprivileged

Run by the R1 lead directly (sub-worker slot unavailable — concurrency cap; see PROVENANCE.md). Time-boxed; gaps are marked honestly.

LOCAL_REPRO environment for every `LOCAL_REPRO` label below: **WSL2, Ubuntu 26.04 LTS, kernel `6.18.33.2-microsoft-standard-WSL2`, uid 1000**. This is a VM, not UEFI bare metal — noted per fact where it matters.

## FACTS

**F1** | Files in `/sys/firmware/efi/efivars/` are prefixed with **4 bytes of UEFI variable attributes in little-endian** before the variable data. A reader that takes byte 0 as the value gets the WRONG answer. | VERIFIED | 0.95 | Kernel docs `Documentation/filesystems/efivarfs.rst`, verbatim: "Practically the output of each efivar is composed of: 4_bytes_of_attributes + efivar_data" and "the first 4 bytes of the output represent the UEFI variable attributes, in little-endian format." Independently corroborated by osquery source (F2). | The SecureBoot check must read 5 bytes and take byte **4**, not byte 0. This is a concrete, citable correctness trap — exactly the kind of thing that produces a confidently wrong `pass`.

**F2** | `/sys/firmware/efi/efivars` is **world readable**, while the older `/sys/firmware/efi/vars` interface is **root only** — and osquery deliberately chose efivars for exactly that reason. | VERIFIED | 0.90 | osquery `osquery/tables/system/linux/secureboot.cpp` at tag 5.15.0, verbatim comment: "Linux has 2 places efivars can be accessed: /sys/firmware/efi/efivars -- Single file, world readable / /sys/firmware/efi/vars -- Split into attributes and data, only root readable ... the benefit of not requiring root outweighs that." Same file reads 5 bytes and takes `efiData.back()`. | Secure Boot state IS establishable as uid 1000. This retires the assumption that Secure Boot posture requires root, and it is corroborating evidence for the host snapshot's SecureBoot=0 / SetupMode=1 reading.

**F3** | osquery's Secure Boot table **silently emits no row** when the efivar read fails: `if (!readFile(efivarPath, efiData, 5).ok()) { return; }` with only a comment that failure "probably means the kernel doesn't support EFI vars". Under-read is logged to TLOG and also returns no value. | VERIFIED | 0.90 | osquery `secureboot.cpp` @5.15.0, `readBoolEfiVar()`. | **This is precisely the anti-pattern the brief calls a critical failure** ("a report that silently omits unreached checks destroys trust"). Mature prior art gets this wrong; our sensor must emit `unknown` with the errno instead. Strong material for the NOTES.md contrast and for the reviewer.

**F4** | `/proc/sys/kernel/tainted` is the taint bitmask; **bit 12 (4096) = 'O', externally-built ("out-of-tree") module loaded**; **bit 13 (8192) = 'E', unsigned module loaded**. 12288 = 4096 + 8192 = both. | VERIFIED | 0.95 | Kernel docs `Documentation/admin-guide/tainted-kernels.rst` (full bit table fetched: bits 0–19, G/P, F, S, R, M, B, U, D, A, W, C, I, O, E, L, K, X, T, N, J). LOCAL_REPRO: `cat /proc/sys/kernel/tainted` → `0`, readable as uid 1000. | The host's 12288 decodes to exactly "unsigned, out-of-tree module loaded" — a real, defensible `fail`/`info` finding for an "unsigned code permitted" check, with the bit decode as evidence. World-readable, so no UNKNOWN path needed for the value itself.

**F5** | `/sys/devices/system/cpu/vulnerabilities/*` are mode **0444 (world readable)**, root-owned, one file per vulnerability, each containing a human-readable status string. | VERIFIED | 0.90 | LOCAL_REPRO: `ls -l /sys/devices/system/cpu/vulnerabilities/` → `-r--r--r-- 1 root root 4096 … gather_data_sampling`, `ghostwrite`, `indirect_target_selection`, `itlb_multihit`, `l1tf`, … Corroborated by the host snapshot, which read all of them as uid 1000. | CPU mitigation posture is a clean, fully-unprivileged check with zero fallback logic. Note the file SET is kernel-version dependent (`ghostwrite`, `indirect_target_selection` are recent) — enumerate the directory, never hardcode a list, or the check silently under-reports on older kernels.

**F6** | Hardening sysctls are readable as uid 1000: `dmesg_restrict`, `kptr_restrict`, `unprivileged_bpf_disabled`, `randomize_va_space`, `modules_disabled` all returned values with no EACCES. | VERIFIED | 0.85 | LOCAL_REPRO: `for f in dmesg_restrict kptr_restrict unprivileged_bpf_disabled randomize_va_space modules_disabled; do cat /proc/sys/kernel/$f; done` → `0`, `1`, `2`, `2`, `0`. Corroborated by the host snapshot reading the same set on the target. | **Critical semantic point: reading `kernel.dmesg_restrict` is NOT the same as being able to run `dmesg`.** On the target, `dmesg_restrict=1` is readable and `dmesg` returns EPERM. The check must report the *policy value* (which we can prove) and must NOT infer it from the failure of `dmesg`.

**F7** | `kptr_restrict=1` makes `/proc/kallsyms` return zeroed addresses to a non-root reader rather than failing. | VERIFIED | 0.85 | LOCAL_REPRO with `kptr_restrict=1`: `head -2 /proc/kallsyms` → `0000000000000000 T srso_alias_untrain_ret` / `0000000000000000 T _stext`. | A worked example of the project's "EACCES ≠ absent" law in its nastiest form: **the read SUCCEEDS and returns plausible-looking data that is not the truth.** Any check that consumes kernel addresses must treat all-zero as "restricted", not as a value. Good NOTES.md material.

**F8** | On a kernel without the lockdown LSM, `/sys/kernel/security/` exists and is `dr-xr-xr-x root root` (traversable by uid 1000) but is **empty** — `cat /sys/kernel/security/lockdown` returns **ENOENT, not EACCES**. | VERIFIED | 0.80 | LOCAL_REPRO: `ls -la /sys/kernel/security/` → `dr-xr-xr-x 2 root root` with only `.`/`..`; `cat /sys/kernel/security/lockdown` → "No such file or directory". Host snapshot shows the target reading `[none]` from the same path as uid 1000. | Two distinct UNKNOWN reasons must be distinguished in evidence: **ENOENT = the feature is not present in this kernel** (a legitimate `info`/`unknown` with a definite reason) vs **EACCES = present but not permitted** (a different reason). Collapsing them into one "could not read" loses the answer.

**F9** | `/sys/firmware/efi` is **absent entirely** on a non-UEFI system, so its existence is the correct UEFI-vs-legacy-BIOS discriminator, and its absence is the correct reason to report Secure Boot as not-applicable rather than failed. | VERIFIED | 0.85 | LOCAL_REPRO: `ls -ld /sys/firmware/efi` → "No such file or directory" on WSL2 (which boots without UEFI). osquery's `kEfiDirectory` constant and its "efivars may not have been mounted" comment corroborate the same discriminator. | Genericity: on a BIOS host, "Secure Boot disabled" would be a *false* `fail`. The correct output is an explicit unknown/info with reason "no UEFI firmware interface present (`/sys/firmware/efi` ENOENT)".

**F10** | `/sys/class/dmi/id/` does not exist at all on WSL2. | VERIFIED | 0.85 | LOCAL_REPRO: `ls -l /sys/class/dmi/id/` → "No such file or directory". | Direct genericity evidence for the machine-description code: every DMI read needs an ENOENT path that yields explicit unknown, not an empty string (contract B6). Also means a local WSL lab can exercise the "no DMI" branch for free.

**F11** | On the target host, TPM presence is established from sysfs but `/dev/tpm0` and `/dev/tpmrm0` are root-only 0600. | LIKELY | 0.70 | Host snapshot (sanitized). LOCAL_REPRO could not corroborate: `ls -l /sys/class/tpm` showed an existing but empty class directory and `/dev/tpm*` was absent (WSL2 has no TPM). I did NOT read `drivers/char/tpm/tpm-sysfs.c` to confirm which TPM sysfs attributes are 0444 — see G5-2. | TPM checks must be sysfs-presence-based (`/sys/class/tpm/tpm0/tpm_version_major`) and must report device-node access as a separate, honest `unknown`. Do not attempt to open `/dev/tpm*`.

## CONTRADICTIONS

**C5-1** — "Secure Boot state requires root / dmidecode / mokutil" (common community claim, and the reason `mokutil` is usually reached for) **vs** osquery's source comment and the kernel's efivarfs layout, which show `/sys/firmware/efi/efivars` is world readable [F2]. **Resolution: unprivileged efivars read wins**, on two independent primary sources (kernel docs + osquery source) plus the target host having already read SecureBoot/SetupMode as uid 1000. `mokutil` becomes an optional cross-check, never the mechanism — it is also absent on many hosts.

**C5-2** — "If the read succeeds, the value is true" **vs** F7, where `kptr_restrict=1` makes `/proc/kallsyms` return a successful read of **zeroed** data. Recorded as a standing hazard rather than a disputed fact: successful-read-with-degraded-content is a third failure mode alongside EACCES and ENOENT, and no prior art I read flags it.

**C5-3** — My own briefing assumption that `/sys/kernel/security` would be root-only **vs** LOCAL_REPRO showing it `dr-xr-xr-x` and traversable, with the lockdown file simply absent [F8]. **Resolution: the observation wins**; the briefing assumption is withdrawn. Consequence: the lockdown check's failure mode is ENOENT (feature absent), not EACCES (permission), on at least some kernels — and on the target it succeeded outright.

## STOLEN_PATTERNS

**P5-1 — efivars 4-byte attribute skip.** Source: kernel `Documentation/filesystems/efivarfs.rst`; implementation confirmed in osquery `osquery/tables/system/linux/secureboot.cpp` @5.15.0 (`readFile(efivarPath, efiData, 5)` then `efiData.back()`). Application: read exactly 5 bytes of `SecureBoot-8be4df61-93ca-11d2-aa0d-00e098032b8c`, require length 5, take byte index 4; 0 → disabled, 1 → enabled, anything else → `unknown` with the raw byte in evidence. Same for `SetupMode-…`. Emit the path read and the byte value as evidence.

**P5-2 — Prefer the world-readable interface over the root-only one.** Source: the osquery comment weighing `/sys/firmware/efi/vars` (root) against `/sys/firmware/efi/efivars` (world readable) and choosing the latter because "the benefit of not requiring root outweighs" the nicer format. Application: generalise it into a design law for the whole sensor — when two paths give the same fact, pick the one that works as uid 1000, and record the rejected path in evidence so a reader knows we did not just fail to try.

**P5-3 — Invert osquery's silent-return.** Source: `secureboot.cpp` `readBoolEfiVar()`, which `return`s with no row on read failure. Application: our runner takes the opposite branch by construction — every registered check emits exactly one finding; a failed read becomes `unknown` carrying the path, the errno and the reason. Cite this contrast in NOTES.md as a place where mature prior art is wrong for our brief.

**P5-4 — Taint bit table as data, not folklore.** Source: `Documentation/admin-guide/tainted-kernels.rst` bit table. Application: embed the bit→letter→meaning table verbatim from kernel docs and decode the integer, so evidence reads `tainted=12288 → bits 12(O: out-of-tree module), 13(E: unsigned module)` rather than a bare number.

**P5-5 — Three distinct not-answered reasons.** Source: F7 / F8 / F9 taken together. Application: the evidence model must separate ENOENT (feature absent → often a legitimate `info`), EACCES (present, not permitted → `unknown`), and read-succeeded-but-restricted (e.g. zeroed kallsyms → `unknown` with the restriction named). Collapsing these is the most likely way this category produces a confidently wrong answer.
