# R1 / Stream S3 — Secrets-on-disk discovery without leaking values; bounded FS traversal

Scope: does the sensor need CONTENT scanning (gitleaks/trufflehog) at all; metadata-only type
detection; "who can read this" from stat + ACL/xattr data with no `getfacl`; bounded traversal
safety patterns. Research + classification only — no implementation code.

LOCAL_REPRO environment: WSL2, Ubuntu 26.04 LTS, kernel 6.18.33.2-microsoft-standard-WSL2,
uid=1000(kldrm), groups include sudo (unused; all probes below are read-only and unprivileged).
Note: `getfacl`, `setfacl`, `getfattr` are ABSENT in this WSL image (only `/usr/sbin/getcap`
present) — which coincidentally mirrors the target host and makes it a fair proxy for the
"no ACL userland" case.

### B. Type detection from the header only (never the secret body)

**F8** | A PEM-armoured file's type is fully determined by its **first line**, whose grammar is
normative in RFC 7468 §3: `preeb = "-----BEGIN " label "-----"`,
`posteb = "-----END " label "-----"`, `labelchar = %x21-2C / %x2E-7E`,
`label = [ labelchar *( ["-" / SP] labelchar ) ]`. The prose additionally fixes the framing:
"There is exactly one space character (SP) separating the 'BEGIN' or 'END' from the label. There
are exactly five hyphen-minus [characters]". | **VERIFIED** | 0.97 |
`https://www.rfc-editor.org/rfc/rfc7468.txt` ABNF at lines 265-299 (preeb L270, posteb L272,
labelchar L296, label L299), framing prose L193-197 + LOCAL_REPRO below | Design impact: we can
classify with a **bounded read of the first ~64 bytes** and never advance into the base64 body.
`labelchar` excludes `0x2D` (`-`) and `0x20` (SP) from the *character* class, admitting them only
as internal separators — so a strict label parser is ~15 lines and cannot be tricked into
over-reading.

**F9** | RFC 7468 §13's label registry gives the exact label→structure mapping we need for the
"detected type" field: `CERTIFICATE` → Certificate (§5), `PRIVATE KEY` → `PrivateKeyInfo`
(PKCS #8, RFC 5208, §10), `ENCRYPTED PRIVATE KEY` → `EncryptedPrivateKeyInfo` (RFC 5958, §11),
`X509 CRL`, `CERTIFICATE REQUEST` (PKCS #10, §7), `PKCS7` (§8). The RFC also states generators
"MUST generate 'CERTIFICATE' labels and MUST NOT generate 'X509 CERTIFICATE' or
'X.509 CERTIFICATE'", but "Parsers SHOULD NOT" reject them — so we accept the legacy aliases.
| **VERIFIED** | 0.94 | `https://www.rfc-editor.org/rfc/rfc7468.txt` label table lines 353-357
(L355 `PRIVATE KEY`/id-pkcs8, L357 `ENCRYPTED PRIVATE KEY`/RFC5958), §5 prose L403-428 |
Design impact: `ENCRYPTED PRIVATE KEY` vs `PRIVATE KEY` is a **posture distinction we can report
for free** from the label alone — an unencrypted PKCS#8 private key is a materially worse finding
than an encrypted one, and we learn it without reading a single byte of key material. The legacy
`BEGIN RSA PRIVATE KEY` / `BEGIN EC PRIVATE KEY` labels are SEC1/PKCS#1 "traditional" OpenSSL
forms, outside the RFC 7468 registry but matched by the same ABNF — treat as
`unencrypted-private-key` unless a `Proc-Type: 4,ENCRYPTED` header follows (RFC 1421 legacy).

**F10** | An OpenSSH-format private key is identified by the armor label
`-----BEGIN OPENSSH PRIVATE KEY-----`; the *decoded* body then begins with
`#define AUTH_MAGIC "openssh-key-v1"` followed by `string ciphername`, `string kdfname`,
`string kdfoptions`, `uint32 number of keys N`, the public keys, and only then the encrypted
private-key blob. | **VERIFIED** | 0.93 |
`https://raw.githubusercontent.com/openssh/openssh-portable/V_10_2_P1/PROTOCOL.key` line 8
(AUTH_MAGIC) and lines 10-19 (header field order); §3 lines 30-45 show the private keys live
in the *final* field | Design impact: **high-value, low-risk probe.** `ciphername` is the 2nd
field of the header; `ciphername == "none"` means the key is **unencrypted on disk**. We can
read this from roughly the first 100 base64 characters — the private key bytes are structurally
at the *end* of the blob and are never in our buffer. This yields "unprotected SSH private key"
as an evidence-backed finding with a mathematically bounded leak risk of zero. See STOLEN_PATTERNS.

**F11** | Binary (non-PEM) key/cert containers are identifiable from 2-4 magic bytes. DER-encoded
X.509 / PKCS#8 / PKCS#12 all begin with an ASN.1 `SEQUENCE` tag `0x30` followed by a long-form
length byte (`0x81`/`0x82`/`0x83`); a real CA certificate in DER starts `30 82 07 d3`. PKCS#12
(`.p12`/`.pfx`) is also a DER SEQUENCE, so byte-level magic distinguishes DER-vs-PEM but **not**
p12-vs-x509 — that requires parsing the OID, which we will not do. | **VERIFIED** | 0.88 |
LOCAL_REPRO below (`openssl x509 -outform DER | xxd` → `3082 07d3`); RFC 7468 §13 table L353-357
confirms all these labels wrap DER/BER structures | Design impact: report DER files as
`der-asn1-container (unclassified)` with the extension as a weak hint, and mark the precise type
`unknown` with reason `would-require-asn1-parse`. **Under-claiming is a bug, but so is guessing:**
extension-based p12 claims are heuristic and must be labelled as such.

### C. "Who can read this?" — permissions, POSIX ACLs without getfacl, capabilities

**F13** | **POSIX ACLs are readable in pure Go with zero CGO and zero external binaries.** The
ACL lives in the `system.posix_acl_access` extended attribute (and `system.posix_acl_default` on
directories) and its on-disk layout is a 4-byte little-endian version header followed by an array
of 8-byte entries. The kernel UAPI is definitive:
`#define POSIX_ACL_XATTR_VERSION 0x0002`, `#define ACL_UNDEFINED_ID (-1)`,
`struct posix_acl_xattr_entry { __le16 e_tag; __le16 e_perm; __le32 e_id; }`,
`struct posix_acl_xattr_header { __le32 a_version; }`. So `len(xattr) == 4 + 8*n`, always. |
**VERIFIED** | 0.97 | primary: `https://raw.githubusercontent.com/torvalds/linux/v6.12/include/uapi/linux/posix_acl_xattr.h`
lines 24, 27, 29-33, 35-37 — **plus LOCAL_REPRO byte-exact decode below** | Design impact: this
retires the "`getfacl` is absent on the target host" blocker completely. `unix.Getxattr(path,
"system.posix_acl_access", buf)` + ~30 lines of `binary.LittleEndian` parsing gives us the real
answer. Validate `a_version == 0x0002` and `(len-4)%8 == 0` and **emit UNKNOWN rather than
guessing** if either fails (forward-compat against a future version 3).

**F14** | LOCAL_REPRO (Ubuntu 26.04, kernel 6.18.33.2-microsoft-standard-WSL2, uid 1000): reading
`system.posix_acl_access` on `/var/log/journal` via `os.getxattr` returned **44 bytes** =
`0200000001000700ffffffff04000500ffffffff080005000400000010000500ffffffff20000500ffffffff`.
Decoded with the F13 struct: `a_version = 0x2`; 5 entries — `ACL_USER_OBJ(0x01) perm=7`,
`ACL_GROUP_OBJ(0x04) perm=5`, `ACL_GROUP(0x08) perm=5 id=4`, `ACL_MASK(0x10) perm=5`,
`ACL_OTHER(0x20) perm=5`. `44 == 4 + 8*5` exactly. `id=4` is gid 4 = `adm`, which is precisely
the systemd-journal ACL grant. | **VERIFIED** | 0.96 | LOCAL_REPRO (command + raw hex above);
struct semantics from the kernel header cited in F13; tag values from `include/uapi/linux/acl.h`
conventions, corroborated by the decode landing on a semantically correct systemd ACL |
Design impact: end-to-end proof, on a machine with **no `getfacl`, no `setfacl`, no `getfattr`
installed at all**, that we can compute effective readability. Also proves the *discovery* step:
`os.Listxattr`/`unix.Listxattr` tells us whether a path has an ACL at all, so we only pay for
the parse where an ACL exists. Note `ACL_MASK` must be intersected with `ACL_USER`/`ACL_GROUP`
entries to get *effective* permissions — reporting the raw entry perms would over-state access.

**F15** | The absence of an ACL is itself reportable and cheap: `os.listxattr("/etc/shadow")`
returned `[]` (empty) on the LOCAL_REPRO host, while `ls -l` showed `-rw-r----- 1 root shadow
777 /etc/shadow`. So `/etc/shadow`'s readability is fully described by mode+owner+group alone:
group `shadow` readable, others not. An unprivileged `head -c 1 /etc/shadow` returned
`Permission denied` with exit 1. | **VERIFIED** | 0.95 | LOCAL_REPRO (three commands above) |
Design impact: **EACCES on a path we can `lstat` is a PASS-grade observation, not an UNKNOWN.**
We learned "root/shadow-only, uid 1000 cannot read it" — that is the *answer* to the posture
question. Contrast with EACCES on a *directory* (F19), which destroys enumeration and IS an
UNKNOWN. The sensor must distinguish "cannot read the file but fully know its protection" from
"cannot list the directory so cannot know what is in it".

**F16** | File **capabilities** live in the `security.capability` xattr and are readable by the

### D. Bounded filesystem traversal (safety requirement, not a nicety)

**F18** | `filepath.WalkDir` is the correct primitive over `filepath.Walk`, on the Go team's own
authority: "Walk is less efficient than [WalkDir], introduced in Go 1.16, **which avoids calling
os.Lstat on every visited file or directory**." Both are documented "does not follow symbolic
links." `WalkDir` hands the callback an `fs.DirEntry`, whose `Type()` comes from the readdir
`d_type` field, so the common case costs no extra syscall; `Info()` is the opt-in `lstat`. |
**VERIFIED** | 0.96 |
`https://raw.githubusercontent.com/golang/go/go1.25.0/src/path/filepath/path.go` — WalkDir
doc L380-394 (no-symlink guarantee at **L390**), `func WalkDir` L395, Walk doc L408-421 with
the efficiency statement at **L420-421**, `func Walk` L422 | Design impact: use `WalkDir`, call
`d.Type()` first and only `d.Info()` when we actually need mode/owner/size. Caveat from the same
doc block (L386-388): "The files are walked in lexical order, which makes the output deterministic
but **requires WalkDir to read an entire directory into memory** before proceeding" — so a
pathological directory with millions of entries is a memory risk. For hostile/unbounded
directories prefer `os.ReadDir` with our own cap, or `(*os.File).ReadDir(n)` for true streaming.
Determinism is otherwise a feature: it makes `findings.json` diffable between runs.

**F19** | **Opening a FIFO blocks forever, and `lstat` is a sufficient pre-check.** LOCAL_REPRO:
`mkfifo`, then `timeout 2 cat <fifo>` ran the full 2 seconds and was killed —
`real 0m2.014s`, `exit=124` (the `timeout` SIGTERM code) — i.e. no writer, no EOF, indefinite
block. The same FIFO: `os.lstat` reported `S_ISFIFO = True`, `mode = 0o10644` **before any
open**; and `os.open(path, O_RDONLY|O_NONBLOCK)` returned immediately (`fd=3`) with
`os.read(fd,10)` returning empty bytes. | **VERIFIED** | 0.95 | LOCAL_REPRO (all four
observations above, in a `mktemp -d` dir, removed afterwards); corroborated by open(2)/fifo(7)
semantics | Design impact: this validates the mandatory pattern — **stat first via `lstat` or
`d.Type()`, and only open paths where `mode.IsRegular()`**, with `O_NONBLOCK|O_NOFOLLOW|O_CLOEXEC`
as belt-and-braces against the TOCTOU window between the stat and the open. This directly
implements the project invariant "only regular files are opened (never device nodes/FIFOs)".
Device nodes are worse than FIFOs: reading `/dev/*` can block *and* have side effects on
hardware. Note `O_NONBLOCK` is not a substitute for the type check — it does not make a device
read safe, it only makes it not hang.

**F20** | `openat2(2)` provides kernel-enforced traversal confinement — `RESOLVE_NO_SYMLINKS`
("Disallow resolution of symbolic links during path resolution. This option implies
RESOLVE_NO_MAGICLINKS.") and `RESOLVE_NO_XDEV` ("Disallow traversal of mount points during path
resolution (including all bind mounts)") — but it was added only in **Linux 5.6**. The man page
notes `RESOLVE_NO_SYMLINKS` differs from `O_NOFOLLOW`, which affects only the final component. |
**VERIFIED** | 0.90 | `https://man7.org/linux/man-pages/man2/openat2.2.html` VERSIONS ("Linux
5.6") and the resolve-flag descriptions | Design impact: the Lava host runs kernel 6.8/7.0, so
`openat2` is available *there* — but "generic by design" means a RHEL 7 (3.10) or CentOS 8 box
would get `ENOSYS`. Therefore: **`openat2` is an optional hardening layer, never the mechanism.**
The portable path (`lstat` + `O_NOFOLLOW|O_NONBLOCK` + explicit `st_dev` comparison) must be the
primary implementation, with `openat2` tried first and `ENOSYS`/`EINVAL` falling back silently
(this is capability detection, not version sniffing).

**F21** | Filesystem-boundary and pseudo-filesystem skipping are doable with stdlib plus
`x/sys`. Compare `Stat_t.Dev` between a directory and its parent to detect a mount crossing (the
`find -xdev` semantic), and/or use `unix.Statfs` and match `Statfs_t.Type` against magic
constants already exported by `golang.org/x/sys/unix`: `PROC_SUPER_MAGIC = 0x9fa0`,
`SYSFS_MAGIC = 0x62656572`, `TMPFS_MAGIC = 0x1021994`, `NFS_SUPER_MAGIC = 0x6969`,

`https://raw.githubusercontent.com/golang/sys/v0.30.0/unix/zerrors_linux.go` lines 2457, 3291,
3484, 2174, 721, 800 respectively | Design impact: we get `-xdev` for free with no new

## CONTRADICTIONS

**C1 — "gitleaks relicensed away from MIT."** *Side A (the stream brief / widely-repeated
belief):* gitleaks moved from MIT to a different licence at some version, making it a licensing
blocker. *Side B (this stream's evidence):* the `LICENSE` file at current HEAD `v8.30.1` is
verbatim MIT, and the file's complete commit history is three commits ending 2019-12-04 — it has
not been touched in ~6 years. The v8.30.1 root tree contains no second licence file. **Resolution:
Side B, high confidence.** Both sides recorded because the belief is common enough that a reviewer
may raise it; the rebuttal is S3-1/S3-2/S3-3. Residual uncertainty: I checked the `LICENSE` file
and the root tree only, not every subdirectory, and I did not check whether a *separate* product
(e.g. a hosted/commercial gitleaks offering) carries different terms — that would not affect
linking the OSS module. **Consequence: gitleaks must be rejected on the safety and weight
arguments (F4, F5, F7), and NOTES.md must not assert a licence change.**

**C2 — Is EACCES an observation or an UNKNOWN?** *Side A:* any errno means we failed, so emit
`unknown`. *Side B (F15):* EACCES on a *file* whose `lstat` succeeded is a complete answer to
"who can read this" — we learned owner, group, mode, and ACL, and that uid 1000 cannot read it.
**Resolution: both are right about different objects.** EACCES on `open(file)` after a successful
`lstat` = PASS/FAIL-grade evidence. EACCES on `opendir`/`readdir` = genuine UNKNOWN, because
enumeration failed and absence is unprovable ("Absence is only provable from a successful
listing"). The sensor needs these as two distinct code paths, and conflating them is the single
most likely correctness bug in this check family.

**C3 — `O_NONBLOCK` vs type-checking for non-regular files.** *Side A:* `O_NONBLOCK` is
sufficient, since LOCAL_REPRO showed it returns immediately on a FIFO (F19). *Side B:*
`O_NONBLOCK` prevents *hanging* but not *side effects* — opening or reading a character device
can perturb hardware, and on some drivers `O_NONBLOCK` is ignored. **Resolution: Side B.** The
type check (`mode.IsRegular()`) is the primary guard and is mandatory; `O_NONBLOCK|O_NOFOLLOW`
is defence-in-depth for the TOCTOU window only. Recorded because the LOCAL_REPRO result could
otherwise be over-read as licence to skip the type check.

## STOLEN_PATTERNS

- **P1 — Central read-limit gate, not per-caller discipline.** Source: osquery
  `osquery/filesystem/filesystem.cpp` L44 (`FLAG(uint64, read_max, 50*1024*1024, ...)`),
  L54-60 (`checkFileReadLimit`), called at L123 / L150 / L178 / L216 @ tag `5.19.0`. *Apply:* one
  internal `boundedRead(path, cap)` helper that every secrets check must go through; it stats
  first, refuses non-regular files, caps bytes, and returns a typed reason on refusal. A file
  larger than the cap yields a finding with `size` recorded and content never read. Tighten the
  cap to KiB scale since we only need headers (F8).
- **P2 — Depth/expansion ceiling as a named constant.** Source: same file, L50
  (`const size_t kMaxRecursiveGlobs = 64;`) with the bound enforced in the loop at L343 and the
  early exit at L350. *Apply:* `maxWalkDepth` and `maxEntriesPerDir` as named, documented
  constants; on exhaustion return `fs.SkipDir` **and emit an UNKNOWN for the truncated subtree**
  rather than treating the truncated walk as complete.
- **P3 — Two-pass xattr sizing.** Source: `joshlf/go-acl` `acl_linux.go` L211-218 — call
  `Getxattr` with a buffer, and on `ERANGE` call again with `nil` to learn the true size, then
  reallocate. *Apply:* same idiom against `system.posix_acl_access`, but with an absolute upper
  bound (an ACL is `4 + 8n` bytes per F13, so a few hundred entries is already absurd — cap it
  and emit UNKNOWN beyond).
- **P4 — Read the OpenSSH `ciphername` field, never the key.** Source: openssh-portable
  `PROTOCOL.key` L8-19 @ `V_10_2_P1`: after `AUTH_MAGIC "openssh-key-v1"` the very next field is
  `string ciphername`, and the private keys are structurally the *last* field (L19, L30-45).
  *Apply:* base64-decode only the first ~48 bytes of the armor body, confirm the magic, read
  `ciphername`; `"none"` means the private key is **unencrypted on disk** — a strong, actionable
  posture finding whose evidence is `ciphername=none` and whose leak risk is provably zero
  because key bytes are never in the buffer. This is the single highest-value technique in this
  stream.
- **P5 — Label-only PEM classification with a strict ABNF.** Source: RFC 7468 L265-299 (`preeb`,
  `label`, `labelchar = %x21-2C / %x2E-7E`) and L193-197 (exactly one SP, exactly five hyphens).
  *Apply:* read the first line up to a hard byte cap, validate the framing exactly, map the label
  via the RFC's own registry table (L353-357) to `detected_type`. Encrypted-vs-plain PKCS#8 falls
  out for free (F9). Refuse to advance past the first newline.
- **P6 — Metadata-only schema with an explicit privilege note.** Source: osquery
  `specs/linux/shadow.table` L2-14 @ `5.19.0` — the table exposes `hash_alg` and
  `password_status` but never the hash, and the description states the privilege requirement.
  *Apply:* mirror both halves: our secrets findings carry `path, detected_type, mode, owner,
  group, size, mtime` and nothing else, and each `unknown` carries the privilege/errno reason in
  its evidence.
- **P7 — Skip filesystems by magic, curate roots like `suid_bin`.** Sources: `x/sys/unix`
  `zerrors_linux.go` L721/800/2174/2457/3291/3484 for the magic numbers;
  `specs/posix/suid_bin.table` L2 ("suid binaries in common locations"). *Apply:* a curated root
  list (`/etc`, `/etc/ssh`, `/root` — expected EACCES, `/home/*/.ssh`, `/var/lib`, service dirs)
  plus `Statfs` magic filtering and `st_dev` comparison, instead of a walk from `/`. Bounded,
  reviewable, and honest about its scope.
