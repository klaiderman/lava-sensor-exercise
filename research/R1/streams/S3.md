# R1 / Stream S3 — Secrets-on-disk discovery without leaking values; bounded FS traversal

Scope: does the sensor need CONTENT scanning (gitleaks/trufflehog) at all; metadata-only type
detection; "who can read this" from stat + ACL/xattr data with no `getfacl`; bounded traversal
safety patterns. Research + classification only — no implementation code.

LOCAL_REPRO environment: WSL2, Ubuntu 26.04 LTS, kernel 6.18.33.2-microsoft-standard-WSL2,
uid=1000(kldrm), groups include sudo (unused; all probes below are read-only and unprivileged).
Note: `getfacl`, `setfacl`, `getfattr` are ABSENT in this WSL image (only `/usr/sbin/getcap`
present) — which coincidentally mirrors the target host and makes it a fair proxy for the
"no ACL userland" case.

### B. Type detection from the header only (never the secret body)

**F8** | A PEM-armoured file's type is fully determined by its **first line**, whose grammar is
normative in RFC 7468 §3: `preeb = "-----BEGIN " label "-----"`,
`posteb = "-----END " label "-----"`, `labelchar = %x21-2C / %x2E-7E`,
`label = [ labelchar *( ["-" / SP] labelchar ) ]`. The prose additionally fixes the framing:
"There is exactly one space character (SP) separating the 'BEGIN' or 'END' from the label. There
are exactly five hyphen-minus [characters]". | **VERIFIED** | 0.97 |
`https://www.rfc-editor.org/rfc/rfc7468.txt` ABNF at lines 265-299 (preeb L270, posteb L272,
labelchar L296, label L299), framing prose L193-197 + LOCAL_REPRO below | Design impact: we can
classify with a **bounded read of the first ~64 bytes** and never advance into the base64 body.
`labelchar` excludes `0x2D` (`-`) and `0x20` (SP) from the *character* class, admitting them only
as internal separators — so a strict label parser is ~15 lines and cannot be tricked into
over-reading.

**F9** | RFC 7468 §13's label registry gives the exact label→structure mapping we need for the
"detected type" field: `CERTIFICATE` → Certificate (§5), `PRIVATE KEY` → `PrivateKeyInfo`
(PKCS #8, RFC 5208, §10), `ENCRYPTED PRIVATE KEY` → `EncryptedPrivateKeyInfo` (RFC 5958, §11),
`X509 CRL`, `CERTIFICATE REQUEST` (PKCS #10, §7), `PKCS7` (§8). The RFC also states generators
"MUST generate 'CERTIFICATE' labels and MUST NOT generate 'X509 CERTIFICATE' or
'X.509 CERTIFICATE'", but "Parsers SHOULD NOT" reject them — so we accept the legacy aliases.
| **VERIFIED** | 0.94 | `https://www.rfc-editor.org/rfc/rfc7468.txt` label table lines 353-357
(L355 `PRIVATE KEY`/id-pkcs8, L357 `ENCRYPTED PRIVATE KEY`/RFC5958), §5 prose L403-428 |
Design impact: `ENCRYPTED PRIVATE KEY` vs `PRIVATE KEY` is a **posture distinction we can report
for free** from the label alone — an unencrypted PKCS#8 private key is a materially worse finding
than an encrypted one, and we learn it without reading a single byte of key material. The legacy
`BEGIN RSA PRIVATE KEY` / `BEGIN EC PRIVATE KEY` labels are SEC1/PKCS#1 "traditional" OpenSSL
forms, outside the RFC 7468 registry but matched by the same ABNF — treat as
`unencrypted-private-key` unless a `Proc-Type: 4,ENCRYPTED` header follows (RFC 1421 legacy).

**F10** | An OpenSSH-format private key is identified by the armor label
`-----BEGIN OPENSSH PRIVATE KEY-----`; the *decoded* body then begins with
`#define AUTH_MAGIC "openssh-key-v1"` followed by `string ciphername`, `string kdfname`,
`string kdfoptions`, `uint32 number of keys N`, the public keys, and only then the encrypted
private-key blob. | **VERIFIED** | 0.93 |
`https://raw.githubusercontent.com/openssh/openssh-portable/V_10_2_P1/PROTOCOL.key` line 8
(AUTH_MAGIC) and lines 10-19 (header field order); §3 lines 30-45 show the private keys live
in the *final* field | Design impact: **high-value, low-risk probe.** `ciphername` is the 2nd
field of the header; `ciphername == "none"` means the key is **unencrypted on disk**. We can
read this from roughly the first 100 base64 characters — the private key bytes are structurally
at the *end* of the blob and are never in our buffer. This yields "unprotected SSH private key"
as an evidence-backed finding with a mathematically bounded leak risk of zero. See STOLEN_PATTERNS.

**F11** | Binary (non-PEM) key/cert containers are identifiable from 2-4 magic bytes. DER-encoded
X.509 / PKCS#8 / PKCS#12 all begin with an ASN.1 `SEQUENCE` tag `0x30` followed by a long-form
length byte (`0x81`/`0x82`/`0x83`); a real CA certificate in DER starts `30 82 07 d3`. PKCS#12
(`.p12`/`.pfx`) is also a DER SEQUENCE, so byte-level magic distinguishes DER-vs-PEM but **not**
p12-vs-x509 — that requires parsing the OID, which we will not do. | **VERIFIED** | 0.88 |
LOCAL_REPRO below (`openssl x509 -outform DER | xxd` → `3082 07d3`); RFC 7468 §13 table L353-357
confirms all these labels wrap DER/BER structures | Design impact: report DER files as
`der-asn1-container (unclassified)` with the extension as a weak hint, and mark the precise type
`unknown` with reason `would-require-asn1-parse`. **Under-claiming is a bug, but so is guessing:**
extension-based p12 claims are heuristic and must be labelled as such.

**F12** | There is **no canonical, machine-readable filename list for credential material** in
the mainstream prior art, because the mainstream prior art is all *content* scanning. Trivy's
built-in rule set (`pkg/fanal/secret/builtin-rules.go`, 849 lines at `v0.58.2`) is keyword-gated
regex over file *contents* — every rule is a `Regex` + `Keywords` pair (e.g. L184-190 private-key,
L236-241 `gcp-service-account` matching the literal string `"type": "service_account"`), and the
file defines ~60 `SecretRuleCategory` constants (L12-31+) but no path/filename rule set. gitleaks
likewise keys on content keywords (F6). | **LIKELY** | 0.80 | Trivy
`https://raw.githubusercontent.com/aquasecurity/trivy/v0.58.2/pkg/fanal/secret/builtin-rules.go`
L12-31, L103-277; gitleaks `config/gitleaks.toml` (no path rules); negative result — I did not
find a filename registry in either | Design impact: **we must own our filename list** and treat it
as a reviewable design artifact, not a borrowed one. The `linPEAS`/`LinEnum` family does encode
such lists, but as inline shell globs rather than a spec, so they are a *source of candidates*,
not an authority. Candidate set (each entry justified individually): `id_rsa`, `id_dsa`,
`id_ecdsa`, `id_ed25519`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `.env`, `.netrc`,
`.pgpass`, `credentials`, `.aws/credentials`, `.docker/config.json`, `.git-credentials`,
`kubeconfig`, `.kube/config`, `.ssh/authorized_keys`, `ssh_host_*_key`. **The filename is a
hint, never the finding**: report `detected_type` from the header when readable, and fall back
to `name-heuristic` with that word in the evidence when it is not.
