# R1 / Stream S4 — BMC in-band access detection from inside the OS, unprivileged

Scope: can this machine talk to its own BMC from inside the OS, through which interface,
and WHO IS PERMITTED to do it. Read-only, uid 1000, no sudo, no network I/O.

Kernel citations pinned to **tag `v6.8`** (matches target host running kernel
`6.8.0-139-generic`) unless a line says otherwise.

LOCAL_REPRO environment: **Ubuntu 26.04 LTS (Resolute Raccoon), kernel
`6.18.33.2-microsoft-standard-WSL2`, uid 1000 (`kldrm`), groups incl. `sudo`** — a VM with
no BMC. Used ONLY to verify the *absence* evidence path and capture exact errno strings.
No `modprobe`, no writes, no ssh.

---

## FACTS

### A. What creates /dev/ipmiN and why it is 0600 root:root

**F1 | `/dev/ipmiN` is created by `ipmi_devintf` via `device_create()` on a class that
registers NO `.devnode` callback, so it carries no mode/uid/gid hint. | VERIFIED | 0.97**
Evidence: `torvalds/linux` @ `v6.8` `drivers/char/ipmi/ipmi_devintf.c:810-812`:
`static const struct class ipmi_class = { .name = "ipmi", };`
and `ipmi_devintf.c:827` inside `ipmi_new_smi()`:
`device_create(&ipmi_class, device, dev, NULL, "ipmi%d", if_num);`
The struct initialiser has exactly one member — no `.devnode`, no `.dev_uevent`.
Design impact: the 0600 we see on the host is **kernel/devtmpfs default behaviour, not a
Supermicro or Latitude.sh hardening choice**. Do not report it as a misconfiguration or as
site policy; report it as the stock Linux default.

**F2 | devtmpfs assigns mode `0600` root:root to any device node whose class/device_type
supplies no devnode mode — this is the documented default. | VERIFIED | 0.97**
Evidence (primary, 3 independent points in-tree):
- `drivers/base/devtmpfs.c:12` (file header comment): "owned by root and have a default
  mode of 0600. Subsystems can" (sentence continues: overwrite the default).
- `drivers/base/devtmpfs.c:122-130`:
  `req.mode = 0;` … `req.name = device_get_devnode(dev, &req.mode, &req.uid, &req.gid, &tmp);`
  … `if (req.mode == 0) req.mode = 0600;`
- `drivers/base/core.c:3913-3931` `device_get_devnode()` only writes `*mode` when
  `dev->type->devnode` or `dev->class->devnode` exists (lines 3922-3929). With neither,
  `req.mode` stays 0 → 0600.

Chained with F1 this is a **closed proof**: `crw------- root root /dev/ipmi0` is the
upstream default for every Linux host with `ipmi_devintf` loaded and no extra udev rule.
Design impact: the sensor must treat "EACCES on /dev/ipmi0" as the EXPECTED, NORMAL state,
not as a finding of misconfiguration. It is `not permitted`, and it is not evidence about
whether the BMC answers.

**F3 | The chrdev name registered for the IPMI major is `"ipmidev"`, while the device node
is named `ipmi%d` — so `/proc/devices` shows `<major> ipmidev`, not `ipmi0`. | VERIFIED | 0.95**
Evidence: `ipmi_devintf.c:792` `#define DEVICE_NAME     "ipmidev"`;
`ipmi_devintf.c:869` `register_chrdev(ipmi_major, DEVICE_NAME, &ipmi_fops);`
vs. the node name `"ipmi%d"` at `ipmi_devintf.c:827`.
LOCAL_REPRO: `/proc/devices` is world-readable —
`-r--r--r-- 1 root root 0 Sep  9 01:38 /proc/devices`.
Design impact: **a second, cheap, always-permitted evidence path.** Grepping
`/proc/devices` for `ipmidev` proves the device interface driver is loaded and holds a
major, even when `/dev/ipmi0` cannot be opened (EACCES). Expected on the target:
`238 ipmidev`. A sensor that only looks at `/dev/ipmi*` misses this. Note the name
mismatch trap: searching `/proc/devices` for `ipmi0` finds nothing.

**F4 | `ipmi_major` is a module parameter defaulting to 0 (dynamic major), so the major
number is NOT a stable identifier. | VERIFIED | 0.93**
Evidence: `ipmi_devintf.c:794-796` `static int ipmi_major;` /
`module_param(ipmi_major, int, 0);` / `MODULE_PARM_DESC(ipmi_major, "Sets the major number
of the IPMI device.  By"…)`; and `ipmi_devintf.c:876-877` `if (ipmi_major == 0) {
ipmi_major = rv;` (adopt the dynamically allocated major).
Design impact: do NOT hardcode 238 (the value observed on the target) as a predicate.
Match on the **name** `ipmidev` in `/proc/devices`, or read `/sys/class/ipmi/ipmi0/dev`.
Reporting "major 238" is fine as *evidence*, never as a *test*.

### B. The unprivileged sysfs evidence path (the load-bearing one)

**F5 | ALL ten BMC identity attributes under `/sys/devices/platform/ipmi_bmc.N/` are
world-readable mode `0444` by upstream declaration. | VERIFIED | 0.98**
Evidence: `drivers/char/ipmi/ipmi_msghandler.c` @ `v6.8` — attribute definitions:
- `:2758`  `static DEVICE_ATTR_RO(device_id);`
- `:2774`  `static DEVICE_ATTR_RO(provides_device_sdrs);`
- `:2789`  `static DEVICE_ATTR_RO(revision);`
- `:2806`  `static DEVICE_ATTR_RO(firmware_revision);`
- `:2824`  `static DEVICE_ATTR_RO(ipmi_version);`
- `:2840`  `static DEVICE_ATTR(additional_device_support, S_IRUGO, add_dev_support_show, NULL);`
- `:2857`  `static DEVICE_ATTR_RO(manufacturer_id);`
- `:2873`  `static DEVICE_ATTR_RO(product_id);`
- `:2893`  `static DEVICE_ATTR(aux_firmware_revision, S_IRUGO, aux_firmware_rev_show, NULL);`
- `:2911`  `static DEVICE_ATTR_RO(guid);`

and the group at `ipmi_msghandler.c:2913-2925` (`bmc_dev_attrs[]`, exactly these ten) and
`:2950-2953` (`bmc_dev_attr_group`).
Mode proof (independent files): `include/linux/device.h:194-197` — "Like DEVICE_ATTR(),
but @_mode is 0444" / `#define DEVICE_ATTR_RO(_name) … __ATTR_RO(_name)`;
`include/linux/sysfs.h:115-118` — `#define __ATTR_RO(_name) { .attr = { .name =
__stringify(_name), .mode = 0444 }, .show = _name##_show, }`. `S_IRUGO` == 0444.
Design impact: **this is the sensor's primary BMC evidence source.** No device node, no
ioctl, no utility, no privilege. Yields interface presence + IPMI version +
manufacturer/product/firmware/GUID. Matches target ground truth (2.0 / 1.5 / 0x002a7c /
0x1d6e / 32 / guid) exactly.

**F6 | Two of those ten attributes are conditionally hidden by `is_visible`, so their
ABSENCE is meaningful data, not an error. | VERIFIED | 0.95**
Evidence: `ipmi_msghandler.c:2927-2948` `bmc_dev_attr_is_visible()`:
`aux_firmware_revision` returns `mode` only if `id.aux_firmware_revision_set`
(`:2935-2940`); `guid` returns `mode` only if `guid_set` (`:2941-2946`); everything else
returns `mode` unconditionally (`:2947`).
Design impact: if `guid` is missing the correct finding is "BMC did not report a GUID"
(a fact about the BMC), NOT `unknown` and NOT an errno. Conversely, `guid` being present
proves the kernel completed a Get Device GUID transaction with the BMC over KCS — i.e.
transitive proof of in-band reachability **by the kernel**. On the target, `guid` IS
present, so in-band reachability is PROVEN without us ever touching `/dev/ipmi0`.

**F7 | Reading these 0444 sysfs attributes triggers a LIVE IPMI transaction to the BMC
(not a cached static string), so a wedged BMC can make an unprivileged `read()` block. |
VERIFIED | 0.9**
Evidence: every `*_show` handler calls `bmc_get_device_id()` at read time, e.g.
`ipmi_msghandler.c:2744-2756` (`device_id_show` → `rv = bmc_get_device_id(NULL, bmc, &id,
NULL, NULL); … sysfs_emit(...)`); `bmc_get_device_id` (`:2737-2741`) →
`__bmc_get_device_id` (`:2604-2647`) → `__get_device_id()` (`:2556-2567`) →
`send_get_device_id_cmd()` (`:2528`). Header comment `ipmi_msghandler.c:309`: "Note that
the product id, manufacturer id, guid, and device id are" (…fetched dynamically).
Design impact: **the "safe" sysfs path is not unconditionally safe.** Even this
unprivileged read needs the sensor's per-check timeout + isolation. Highest-value
operational fact in this stream: an implementer who assumes "sysfs read == instant" ships
a sensor that stalls on a dead BMC. Bounded, not infinite (kernel has a validity window,
an in-flight guard, and its own IPMI timeouts — F14), but orders of magnitude slower than
a normal file read.
