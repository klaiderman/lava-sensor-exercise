# R1 / Stream S4 — BMC in-band access detection from inside the OS, unprivileged

Scope: can this machine talk to its own BMC from inside the OS, through which interface,
and WHO IS PERMITTED to do it. Read-only, uid 1000, no sudo, no network I/O.

Kernel citations pinned to **tag `v6.8`** (matches target host running kernel
`6.8.0-139-generic`) unless a line says otherwise.

LOCAL_REPRO environment: **Ubuntu 26.04 LTS (Resolute Raccoon), kernel
`6.18.33.2-microsoft-standard-WSL2`, uid 1000 (`kldrm`), groups incl. `sudo`** — a VM with
no BMC. Used ONLY to verify the *absence* evidence path and capture exact errno strings.
No `modprobe`, no writes, no ssh.

---

## FACTS

### A. What creates /dev/ipmiN and why it is 0600 root:root

**F1 | `/dev/ipmiN` is created by `ipmi_devintf` via `device_create()` on a class that
registers NO `.devnode` callback, so it carries no mode/uid/gid hint. | VERIFIED | 0.97**
Evidence: `torvalds/linux` @ `v6.8` `drivers/char/ipmi/ipmi_devintf.c:810-812`:
`static const struct class ipmi_class = { .name = "ipmi", };`
and `ipmi_devintf.c:827` inside `ipmi_new_smi()`:
`device_create(&ipmi_class, device, dev, NULL, "ipmi%d", if_num);`
The struct initialiser has exactly one member — no `.devnode`, no `.dev_uevent`.
Design impact: the 0600 we see on the host is **kernel/devtmpfs default behaviour, not a
Supermicro or Latitude.sh hardening choice**. Do not report it as a misconfiguration or as
site policy; report it as the stock Linux default.

**F2 | devtmpfs assigns mode `0600` root:root to any device node whose class/device_type
supplies no devnode mode — this is the documented default. | VERIFIED | 0.97**
Evidence (primary, 3 independent points in-tree):
- `drivers/base/devtmpfs.c:12` (file header comment): "owned by root and have a default
  mode of 0600. Subsystems can" (sentence continues: overwrite the default).
- `drivers/base/devtmpfs.c:122-130`:
  `req.mode = 0;` … `req.name = device_get_devnode(dev, &req.mode, &req.uid, &req.gid, &tmp);`
  … `if (req.mode == 0) req.mode = 0600;`
- `drivers/base/core.c:3913-3931` `device_get_devnode()` only writes `*mode` when
  `dev->type->devnode` or `dev->class->devnode` exists (lines 3922-3929). With neither,
  `req.mode` stays 0 → 0600.

Chained with F1 this is a **closed proof**: `crw------- root root /dev/ipmi0` is the
upstream default for every Linux host with `ipmi_devintf` loaded and no extra udev rule.
Design impact: the sensor must treat "EACCES on /dev/ipmi0" as the EXPECTED, NORMAL state,
not as a finding of misconfiguration. It is `not permitted`, and it is not evidence about
whether the BMC answers.

**F3 | The chrdev name registered for the IPMI major is `"ipmidev"`, while the device node
is named `ipmi%d` — so `/proc/devices` shows `<major> ipmidev`, not `ipmi0`. | VERIFIED | 0.95**
Evidence: `ipmi_devintf.c:792` `#define DEVICE_NAME     "ipmidev"`;
`ipmi_devintf.c:869` `register_chrdev(ipmi_major, DEVICE_NAME, &ipmi_fops);`
vs. the node name `"ipmi%d"` at `ipmi_devintf.c:827`.
LOCAL_REPRO: `/proc/devices` is world-readable —
`-r--r--r-- 1 root root 0 Sep  9 01:38 /proc/devices`.
Design impact: **a second, cheap, always-permitted evidence path.** Grepping
`/proc/devices` for `ipmidev` proves the device interface driver is loaded and holds a
major, even when `/dev/ipmi0` cannot be opened (EACCES). Expected on the target:
`238 ipmidev`. A sensor that only looks at `/dev/ipmi*` misses this. Note the name
mismatch trap: searching `/proc/devices` for `ipmi0` finds nothing.

**F4 | `ipmi_major` is a module parameter defaulting to 0 (dynamic major), so the major
number is NOT a stable identifier. | VERIFIED | 0.93**
Evidence: `ipmi_devintf.c:794-796` `static int ipmi_major;` /
`module_param(ipmi_major, int, 0);` / `MODULE_PARM_DESC(ipmi_major, "Sets the major number
of the IPMI device.  By"…)`; and `ipmi_devintf.c:876-877` `if (ipmi_major == 0) {
ipmi_major = rv;` (adopt the dynamically allocated major).
Design impact: do NOT hardcode 238 (the value observed on the target) as a predicate.
Match on the **name** `ipmidev` in `/proc/devices`, or read `/sys/class/ipmi/ipmi0/dev`.
Reporting "major 238" is fine as *evidence*, never as a *test*.

- `:2758`  `static DEVICE_ATTR_RO(device_id);`
- `:2774`  `static DEVICE_ATTR_RO(provides_device_sdrs);`
- `:2789`  `static DEVICE_ATTR_RO(revision);`

- `:2857`  `static DEVICE_ATTR_RO(manufacturer_id);`
- `:2873`  `static DEVICE_ATTR_RO(product_id);`
- `:2893`  `static DEVICE_ATTR(aux_firmware_revision, S_IRUGO, aux_firmware_rev_show, NULL);`
- `:2911`  `static DEVICE_ATTR_RO(guid);`

and the group at `ipmi_msghandler.c:2913-2925` (`bmc_dev_attrs[]`, exactly these ten) and
`:2950-2953` (`bmc_dev_attr_group`).
Mode proof (independent files): `include/linux/device.h:194-197` — "Like DEVICE_ATTR(),
but @_mode is 0444" / `#define DEVICE_ATTR_RO(_name) … __ATTR_RO(_name)`;
`include/linux/sysfs.h:115-118` — `#define __ATTR_RO(_name) { .attr = { .name =
__stringify(_name), .mode = 0444 }, .show = _name##_show, }`. `S_IRUGO` == 0444.
Design impact: **this is the sensor's primary BMC evidence source.** No device node, no
ioctl, no utility, no privilege. Yields interface presence + IPMI version +
manufacturer/product/firmware/GUID. Matches target ground truth (2.0 / 1.5 / 0x002a7c /
0x1d6e / 32 / guid) exactly.

**F6 | Two of those ten attributes are conditionally hidden by `is_visible`, so their
ABSENCE is meaningful data, not an error. | VERIFIED | 0.95**
Evidence: `ipmi_msghandler.c:2927-2948` `bmc_dev_attr_is_visible()`:
`aux_firmware_revision` returns `mode` only if `id.aux_firmware_revision_set`
(`:2935-2940`); `guid` returns `mode` only if `guid_set` (`:2941-2946`); everything else
returns `mode` unconditionally (`:2947`).
Design impact: if `guid` is missing the correct finding is "BMC did not report a GUID"
(a fact about the BMC), NOT `unknown` and NOT an errno. Conversely, `guid` being present
proves the kernel completed a Get Device GUID transaction with the BMC over KCS — i.e.
transitive proof of in-band reachability **by the kernel**. On the target, `guid` IS
present, so in-band reachability is PROVEN without us ever touching `/dev/ipmi0`.

**F7 | Reading these 0444 sysfs attributes triggers a LIVE IPMI transaction to the BMC
(not a cached static string), so a wedged BMC can make an unprivileged `read()` block. |
VERIFIED | 0.9**
Evidence: every `*_show` handler calls `bmc_get_device_id()` at read time, e.g.
`ipmi_msghandler.c:2744-2756` (`device_id_show` → `rv = bmc_get_device_id(NULL, bmc, &id,
NULL, NULL); … sysfs_emit(...)`); `bmc_get_device_id` (`:2737-2741`) →
`__bmc_get_device_id` (`:2604-2647`) → `__get_device_id()` (`:2556-2567`) →
`send_get_device_id_cmd()` (`:2528`). Header comment `ipmi_msghandler.c:309`: "Note that
the product id, manufacturer id, guid, and device id are" (…fetched dynamically).
Design impact: **the "safe" sysfs path is not unconditionally safe.** Even this
unprivileged read needs the sensor's per-check timeout + isolation. Highest-value
operational fact in this stream: an implementer who assumes "sysfs read == instant" ships
a sensor that stalls on a dead BMC. Bounded, not infinite (kernel has a validity window,
an in-flight guard, and its own IPMI timeouts — F14), but orders of magnitude slower than
a normal file read.

### C. What ipmi_si does at probe: discovery order and sysfs exposure

**F8 | `ipmi_si` discovery is a fixed init order: platform (which covers ACPI, DMI/SMBIOS
and OpenFirmware/device-tree) then PCI then PA-RISC. | VERIFIED | 0.92**
Evidence: `drivers/char/ipmi/ipmi_si_intf.c:2093-2109` in `init_ipmi_si()`:
`ipmi_si_platform_init();` (`:2105`), `ipmi_si_pci_init();` (`:2107`),
`ipmi_si_parisc_init();` (`:2109`).
Each source is individually gateable by module param:
`ipmi_si_platform.c:24-54` — `si_tryplatform` (`:24`, default true), `si_tryacpi` (`:26`,
default true under `CONFIG_ACPI`), `si_tryopenfirmware` (`:29`, `CONFIG_OF`),
`si_trydmi` (`:32` true under `CONFIG_DMI`, `:34` false otherwise), each exposed via
`module_param_named(..., 0)` at `:37-54`.
Design impact: on the target both an ACPI source and a DMI source were found, which is
exactly the documented dual-discovery case. The sensor should report the **addr_source**,
not just "IPMI present" — see F9.

**F9 | ACPI beats SMBIOS on duplicate detection, and the kernel logs which source won.
This explains the target's simultaneous `IPI0001` + `dmi-ipmi-si.0` evidence. | VERIFIED | 0.9**
Evidence: `ipmi_si_intf.c:1902-1920`:

    dup = find_dup_si(new_smi);
    if (dup) {
        if (new_smi->io.addr_source == SI_ACPI &&
            dup->io.addr_source == SI_SMBIOS) {
            /* We prefer ACPI over SMBIOS. */
            ... "Removing SMBIOS-specified %s state machine in favor of ACPI"

plus `:1922-1924` `pr_info("Adding %s-specified %s state machine\n", ...)` and the type
name table `ipmi_si_intf.c:74`:
`const char *const si_to_str[] = { "invalid", "kcs", "smic", "bt", NULL };`
Design impact: the interface-type string the sensor should report (`kcs`/`smic`/`bt`) comes
from this exact table; the sysfs `type` attribute emits it via `sysfs_emit(buf, "%s\n",
si_to_str[smi_info->io.si_type])` at `ipmi_si_intf.c:1617`. Report `kcs` because sysfs said
`kcs`, not because ACPI `_IFT` was 1. Note: the ACPI/DMI arbitration messages go to
**dmesg**, and on the target `kernel.dmesg_restrict=1` — that corroboration is UNREADABLE
for us (see GAPS).

**F10 | The kernel doc `Documentation/driver-api/ipmi.rst` never documents the `/dev/ipmiN`
node name, its permissions, or any group convention. | VERIFIED | 0.85**
Evidence: `Documentation/driver-api/ipmi.rst` @ `v6.8` — grep for
`dev/ipmi|permission|udev` returns only `:103` ("ipmi_devintf - This provides a userland
IOCTL interface for the IPMI…") and `:107` ("ipmi_si - A driver for various system
interfaces.  This supports KCS,…"). Every other hit is a module-parameter or
`/sys/module/...` reference (`:398`, `:468-476`, `:501`).
Design impact: there is **no upstream-blessed access-control story for in-band IPMI at
all**. That is why "who is permitted" is a genuine posture finding rather than a solved
problem: upstream ships root-only and documents nothing.

### D. WHO IS PERMITTED — the access-control answer

**F11 | Neither the kernel nor upstream systemd/udev ships a rule granting a group access
to `/dev/ipmiN`; there is no conventional `ipmi` group. Access is root-only unless a local
admin adds a custom rule. | LIKELY | 0.72**
Evidence: (a) the F1+F2 chain proves the kernel/devtmpfs default is 0600 root:root with no
class `devnode` override. (b) `Documentation/driver-api/ipmi.rst` is silent (F10).
(c) Debian bug #866574 and the Thomas-Krenn "Configuring IPMI under Linux using ipmitool"
wiki both describe root-only access as the normal, expected state and offer only ad-hoc
`chmod`/custom-rule workarounds — no packaged rule.
Downgraded to LIKELY, not VERIFIED: I could not enumerate the Debian/Ubuntu `openipmi` and
`freeipmi` package file lists directly (GitHub code-search API rate-limited mid-run — see
GAPS), so "no distro ships a rule" rests on absence of evidence for that one clause.
Design impact: phrase the finding as **"in-band IPMI is restricted to uid 0 (stock
default)"**, with node mode + owner + group as evidence, and report the *mechanism* so a
host that HAS relaxed it becomes a distinct, more interesting finding rather than a
silent pass.

**F12 | Even a relaxed, world-READABLE `/dev/ipmi0` would be insufficient: the interface
requires `O_RDWR`, because a request is written and a response read back. "Who is
permitted" must therefore be evaluated as WRITE permission, not read. | VERIFIED | 0.95**
Evidence (2 independent clients, both open read-write):
- ipmitool `src/plugins/open/open.c:107` `intf->fd = open(ipmi_dev, O_RDWR);` (also `:110`
  and `:112` for the two fallback paths) — `github.com/ipmitool/ipmitool` @ `master`.
- u-root `pkg/ipmi/ipmi_linux.go:12-25`:
  `// OpenPath opens a channel to an IPMI device by path (e.g., /dev/ipmi0).` /
  `f, err := os.OpenFile(path, os.O_RDWR, 0)` / `func Open(devnum int)` →
  `OpenPath(fmt.Sprintf("/dev/ipmi%d", devnum))`.
Design impact: the permission predicate is `R_OK|W_OK`-equivalent on the node — evaluate
mode bits for **both** r and w against our uid/gid/supplementary groups. A check that only
asks "can I read it" would over-claim permission. Do this by `stat` + mode arithmetic, not
by attempting `open()` (see STOLEN_PATTERNS: opening is itself a write-capable action and
also arms the hang surface of F14).

**F13 | `ipmitool` tries exactly three device paths in a fixed order and — because it
clobbers `errno` — reports EACCES as ENOENT ("No such file or directory"). This is
verifiable prior art getting the "not permitted vs. absent" distinction WRONG. | VERIFIED | 0.95**
Evidence: `github.com/ipmitool/ipmitool` @ `master`, `src/plugins/open/open.c:102-118`:

    102	sprintf(ipmi_dev, "/dev/ipmi%d", devnum);
    103	sprintf(ipmi_devfs, "/dev/ipmi/%d", devnum);
    104	sprintf(ipmi_devfs2, "/dev/ipmidev/%d", devnum);
    107	intf->fd = open(ipmi_dev, O_RDWR);
    109	if (intf->fd < 0) {
    110		intf->fd = open(ipmi_devfs, O_RDWR);
    111		if (intf->fd < 0) {
    112			intf->fd = open(ipmi_devfs2, O_RDWR);
    113		}
    114		if (intf->fd < 0) {
    115			lperror(LOG_ERR, "Could not open device at %s or %s or %s",
    116			        ipmi_dev, ipmi_devfs, ipmi_devfs2);

`lperror` prints `strerror(errno)`, and `errno` at that point belongs to the **last**
`open()` (`/dev/ipmidev/0`, which does not exist → ENOENT), not the first (EACCES).
Independent confirmation: Debian bug #866574, "ipmitool gives misleading error for EACCESS
on /dev/ipmi0" — reported output is
`Could not open device at /dev/ipmi0 or /dev/ipmi/0 or /dev/ipmidev/0: No such file or
directory` while the true first failure was EACCES on a `crw-------` node.
This is exactly our target host's configuration (`/dev/ipmi0` 0600 root:root,
`/dev/ipmidev/` absent) — so **ipmitool on our host would print "No such file or
directory" for a device that demonstrably exists.**
Design impact: (1) capture-errno-per-path is mandatory (STOLEN_PATTERNS P1); (2) the
three-path list is worth reusing as a `stat` set, but each path's errno must be retained
separately; (3) never let a later probe's errno overwrite an earlier one. This single
finding is the strongest justification in this stream for BUILD over REUSE.

### E. Hang risk and the minimal bounded query

**F14 | The KCS state machine's own timeouts are 5 s per IBF wait and 5 s per OBF wait,
with up to 10 error retries and a 2-second ERROR0 wait — so a non-answering BMC can hold a
single transaction inside the kernel for tens of seconds. | VERIFIED | 0.93**
Evidence: `drivers/char/ipmi/ipmi_kcs_sm.c` @ `v6.8`:
- `:103` `#define IBF_RETRY_TIMEOUT (5*USEC_PER_SEC)`
- `:104` `#define OBF_RETRY_TIMEOUT (5*USEC_PER_SEC)`
- `:105` `#define MAX_ERROR_RETRIES 10`
- `:106` `#define ERROR0_OBF_WAIT_JIFFIES (2*HZ)`
- timeout decrement/expiry logic at `:224-232` (IBF) and `:240-248` (OBF); retry counting
  at `:195-203` (`kcs->error_retries++; if (... > MAX_ERROR_RETRIES)`, else
  `error0_timeout = jiffies + ERROR0_OBF_WAIT_JIFFIES` and enter `KCS_ERROR0`); error
  recovery states at `:449-466`; re-init on failure at `:504`.
Message layer above KCS: `ipmi_msghandler.c:121` `#define MAX_MSG_TIMEOUT 60000` (ms),
`:143` `static unsigned int default_max_retries = 4;` (module param `:144`), `:161`
`#define IPMI_TIMEOUT_TIME 1000`.
Design impact: **the whole-scan deadline must assume a BMC-touching check can cost tens of
seconds, and our per-check timeout must be shorter than the kernel's.** Critically, the
sensor cannot cancel an in-progress kernel `read()`: a Go per-check `context` deadline lets
the *scan* continue and emit `unknown` with reason TIMEOUT, but the reading goroutine stays
blocked until the kernel returns. Budget for that as a bounded goroutine leak in a
single-shot process that then exits — do not `Wait()` on it.

**F15 | On a host where `/dev/ipmi0` IS openable by our uid, the minimal bounded read-only
in-band query is Get Device ID: NetFn App (0x06), cmd 0x01, zero request data — the
canonical no-side-effect probe, and the one the kernel itself issues. | VERIFIED | 0.9**
Evidence (kernel, primary): `ipmi_msghandler.c:2528` `send_get_device_id_cmd(struct
ipmi_smi *intf)`, response handler `bmc_device_id_handler` (`:2487-2508`) calling
`ipmi_demangle_device_id(msg->msg.netfn, msg->msg.cmd, ...)` (`:2508`), with the malformed
path at `:2496` printing `"invalid device_id msg: addr_type=%d netfn=%x cmd=%x\n"`.
The Go ioctl surface it would require (u-root, `main`):
`pkg/ipmi/ipmi.go:26-27` `_IPMICTL_RECEIVE_MSG_TRUNC = ioctl.IOWR(_IPMI_IOC_MAGIC, 11, ...)`,
`_IPMICTL_SEND_COMMAND = ioctl.IOR(_IPMI_IOC_MAGIC, 13, ...)`; used at
`pkg/ipmi/dev.go:68` (send, `unix.SYS_IOCTL` + `unsafe.Pointer`) and `:82` (receive), with
a response-length guard at `:94-95` (`if resp.msg.DataLen >= _IPMI_BUF_SIZE`).
Design impact: **do not implement this.** F5/F6 already deliver the same Get-Device-ID
payload (IPMI version, manufacturer, product, firmware revision, device revision, GUID)
through 0444 sysfs with no privilege, no ioctl, no device write and a smaller hang surface.
The ioctl path adds an `unsafe.Pointer` struct ABI, a write to a device node, and a second
hang surface for zero additional information. It is strictly dominated on our host and on
any host where sysfs is present.

**F16 | The IPMI v2.0 spec itself instructs implementers to add a timeout because BMCs are
known to miss generating interrupts on error — i.e. "the BMC may never answer" is a
spec-acknowledged condition, not an edge case. | VERIFIED | 0.92**
Evidence: *IPMI — Intelligent Platform Management Interface Specification, Second
Generation, v2.0, Document Revision 1.1, October 1, 2013* (Intel/Hewlett-Packard/NEC/Dell),
**§9.20 "KCS Driver Design Recommendations"**, verbatim:
> "It is recommended that cross-platform drivers or software make provision for BMC
> implementations that may miss generating interrupts on a command error condition by
> having a timeout that will activate the driver or software in case an expected interrupt
> is not received."

Get Device ID is confirmed as NetFn **App = 06h** (spec command-table row
"Broadcast `Get Device ID'[1] … App 06h") and **§20.1 "Get Device ID Command"** shows
`Request Data  -  -` — i.e. **zero request bytes**, which is why it is the safe probe.
KCS interface chapter for reference: **§9.1–§9.20** (§9.5 KCS Interface Registers, §9.6
KCS Interface Control Codes, §9.11 Performing KCS Interface Message Transfers, §9.15 KCS
Flow Diagrams, §9.20 driver recommendations).
Design impact: our bounded/timeout invariant is not merely defensive engineering — it is
the behaviour the governing specification prescribes. Cite this in NOTES.md if the timeout
budget is questioned.

### F. SMBIOS/DMI evidence: the directory name IS the data

**F17 | Every file under `/sys/firmware/dmi/entries/<type>-<instance>/` is mode `0400`
(root only) — including `type`, `length`, `instance`, `position` and `raw`. | VERIFIED | 0.96**
Evidence: `drivers/firmware/dmi-sysfs.c` @ `v6.8`, both attribute-defining macros:
- `:57-61` `#define DMI_SYSFS_ATTR(_entry, _name) … .attr = {.name = __stringify(_name),
  .mode = 0400 },`
- `:74-78` `#define DMI_SYSFS_MAPPED_ATTR(_entry, _name) … .attr = {.name =
  __stringify(_name), .mode = 0400 },`

Design impact: matches the target ground truth ("raw tables are root-only"). Do NOT plan on
parsing SMBIOS type 38/42 contents unprivileged. Also do not shell out to `dmidecode`
(needs root for `/dev/mem` or the same 0400 files) — LOCAL_REPRO confirms it may not even
be installed (`command -v dmidecode` → exit 1).

**F18 | …BUT the entry DIRECTORY is mode `0755` and is NAMED `<type>-<instance>`, so an
unprivileged process can prove SMBIOS Type 38 and Type 42 EXIST purely by listing
`/sys/firmware/dmi/entries`, without reading a single byte of table content. | VERIFIED | 0.94**
Evidence:
- Naming, primary: `dmi-sysfs.c:607-608`
  `*ret = kobject_init_and_add(&entry->kobj, &dmi_sysfs_entry_ktype, NULL, "%d-%d",
  dh->type, entry->instance);` and the kset at `:666`
  `dmi_kset = kset_create_and_add("entries", NULL, dmi_kobj);`
- Documented intent, `dmi-sysfs.c:11-14` (header comment): "DMI attributes are presented in
  attribute files with names formatted using %d-%d, so that the first integer indicates the
  structure type (0-255), and the second field is the instance of that entry."
- Directory mode: `fs/sysfs/dir.c:59` `kn = kernfs_create_dir_ns(parent,
  kobject_name(kobj), 0755, uid, gid, …);` — world-readable and world-traversable.

Design impact: **this is the highest-leverage non-obvious finding in the stream.** The
sensor gets "firmware declares an IPMI device (Type 38)" and "firmware declares a
Management Controller Host Interface (Type 42)" from a `readdir` — the cheapest possible
evidence, no exec, no privilege, no hang risk (unlike F7, this really is a plain VFS
operation). Present on the target as `38-0` and `42-0`. This is a genuine
capability-detection primitive that also degrades cleanly: on WSL2 the whole path is
absent (LOCAL_REPRO F21).

**F19 | DSP0134 section numbers and the Type 42 interface-type value we need. | VERIFIED | 0.95**
Evidence: DMTF **DSP0134 SMBIOS Reference Specification v3.8.0** (extracted locally with
`pdftotext -layout`):
- **§7.39 "IPMI Device Information (Type 38)"**, structure layout **Table 114**; byte 01h
  `Length` = 38 → "IPMI Device Information structure indicator".
- **§7.39.1 "IPMI Device Information — BMC Interface Type"**, **Table 115**, verbatim
  values: `00h Unknown`, `01h KCS: Keyboard Controller Style`, `02h SMIC: Server
  Management Interface Chip`, `03h BT: Block Transfer`, `04h SSIF: SMBus System
  Interface`, `05h to 0FFh Reserved`.
- **§7.43 "Management Controller Host Interface (Type 42)"**, structure **Table 122**,
  protocol records **Table 123**; **§7.43.1 Table 124 "Management Controller Host Interface
  Types"** — `00h–3Fh` MCTP Host Interfaces (DSP0239), **`40h` Network Host Interface —
  "See DSP0270 for the definition and details of the Network Host Interface type"**,
  `F0h` OEM-defined, all others Reserved; **§7.43.2 Table 125 "Protocol Types"**.
- DSP0134 §7.43 note: "Type 42 should be used for management controller host interfaces
  that use protocols other than IPMI or …" and the Type 42 structure "can also be used to
  describe a physical management controller host interface".
- Also relevant: Type 42 gained an "Interface Type Specific Data Length" field in SMBIOS
  3.2, and "The addition of the Interface Type Specific Data Length field may cause parser
  compatibility issue in versions earlier than SMBIOS 3.2 when Interface Type = OEM"
  (§7.43, notes 2086-2089) — a parsing hazard we avoid entirely by F18 (name-only).

### G. Redfish over the host interface — detection only

**F20 | Type 42 with Interface Type 40h advertises a Redfish/Network Host Interface, and
DSP0270 defines credential bootstrapping over IPMI — which makes "who may open
/dev/ipmi0" a privilege-relevant question, not just an inventory question. But reaching the
Redfish service requires network I/O, which our sensor forbids. Detection only. | VERIFIED | 0.88**
Evidence: DMTF **DSP0270 "Redfish Host Interface Specification" v1.3.0** (extracted
locally), table of contents and body:
- **§8 "SMBIOS support"**, **§8.1 "SMBIOS Type 42 structure general layout"**,
  **§8.2 Table 1 "SMBIOS Type 42 structure definition for Redfish Host Interfaces"**.
- Device descriptor variants: **§8.3.2 Table 4 "Device Descriptor Data for Device Type 02h
  (USB Network Interface)"**, §8.3.3 Table 5 (PCI/PCIe Network Interface, Device Type 03h),
  §8.3.4 Table 6 (USB Network Interface v2, 04h), §8.3.5 Table 7 (PCI/PCIe v2, 05h),
  §8.3.6 Table 8 (OEM, 80h–FFh). **Device Type 02h/04h = USB Network Interface is the
  variant matching the target's aspeed_vhub RNDIS gadget.**
- **§8.4.3 Table 13 "IP Address Format values"** — the type 42 blob carries the BMC-side IP
  configuration, i.e. the Redfish service entry point address.
- **§9 "Credential bootstrapping via IPMI commands"**, **§9.1.2 "Get Bootstrap Account
  Credentials (NetFn 2Ch, Command 02h)"**.
- DSP0134 v3.8.0 references "DMTF DSP0270, Redfish Host Interface Specification 1.3.0".

Design impact, three parts:
1. **Report, do not connect.** The sensor must never issue HTTP to the BMC. The finding is
   "firmware advertises a Redfish host interface (SMBIOS Type 42)" + "a BMC-side USB NIC
   exists and its operstate is DOWN with no address" — both from sysfs reads.
2. **The USB NIC being DOWN is a genuine, reportable posture fact**, and it is *stronger*
   evidence than absence: `rndis_host` bound to `0b1f:03ee` on `aspeed_vhub` proves the
   path is physically present and merely not configured. "Present but disabled" ≠ "absent".
3. **Security framing:** because DSP0270 §9.1.2 lets an in-band caller with IPMI access
   retrieve Redfish account credentials, `/dev/ipmi0` write access is effectively a
   credential-issuing capability. That elevates F11/F12 from trivia to the actual point of
   the check: enumerating *who* may open that node is enumerating who can mint BMC
   credentials. This is the sentence worth putting in NOTES.md.

### H. ABSENCE vs NOT-PERMITTED — the evidence rules

**F21 | LOCAL_REPRO: on a BMC-less machine every BMC evidence path is absent with ENOENT,
and the exact strings are stable and distinguishable from EACCES. | VERIFIED | 0.95**
Evidence — LOCAL_REPRO, Ubuntu 26.04 LTS, kernel `6.18.33.2-microsoft-standard-WSL2`,
`uid=1000(kldrm) gid=1000(kldrm) groups=1000,4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users)`.
Verbatim observed output:

    $ ls -l /sys/class/ipmi
    ls: cannot access '/sys/class/ipmi': No such file or directory
    $ ls -l /dev/ipmi*
    ls: cannot access '/dev/ipmi*': No such file or directory
    $ cat /dev/ipmi0
    cat: /dev/ipmi0: No such file or directory        (exit 1)
    $ ls -l /dev/ipmidev
    ls: cannot access '/dev/ipmidev': No such file or directory   (exit 2)
    $ lsmod | grep -i ipmi
    (no output, grep exit 1)
    $ ls /sys/module | grep -i ipmi
    (no output, grep exit 1)
    $ ls /sys/devices/platform
    MSFT1002:00  intel_rapl_msr.0  kgdboc  power  serial8250  uevent
    $ ls /sys/firmware/dmi/entries
    ls: cannot access '/sys/firmware/dmi/entries': No such file or directory

Note `/sys/firmware` exists but contains only `acpi` and `memmap` — **no `dmi` subdirectory
at all**, because WSL2 exposes no SMBIOS entry point. So the sensor must distinguish
"`/sys/firmware/dmi` missing" (no SMBIOS at all — a platform fact) from
"`/sys/firmware/dmi/entries` present but no `38-*` dir" (SMBIOS present, firmware declares
no IPMI device — a much stronger claim).
Design impact: these are the literal evidence strings to emit. All are ENOENT. None is
EACCES. The two are trivially separable at the syscall level and must never be merged.

**F22 | The absence rule: "no in-band BMC" is only provable from a conjunction of
SUCCESSFUL listings; any single EACCES in the conjunction downgrades the whole finding to
`unknown`. | VERIFIED (by derivation from F1-F21) | 0.9**
Proposed decision table for the sensor (this is the deliverable of this stream):

| Observation set | Finding | Reason |
|---|---|---|
| `/sys/devices/platform/ipmi_bmc.*` readable, attrs parse | **in-band BMC present AND kernel can talk to it** | F5, F6 — kernel completed Get Device ID/GUID |
| `/sys/class/ipmi/ipmi*` exists, `/dev/ipmi0` exists but mode denies our uid/gid | **present, NOT PERMITTED to us** (this is the target host) | F1, F2, F12 — stock default, evaluate r+w |
| `stat("/dev/ipmi0")` → EACCES *on the parent dir* | **`unknown`, reason=EACCES** — NOT absence | F13 anti-pattern |
| `/sys/firmware/dmi/entries/38-*` present | **firmware declares an IPMI device** | F18, F19 §7.39 |
| `/sys/firmware/dmi/entries` listed OK and no `38-*` | **firmware declares no IPMI device** (provable negative) | F18 — absence from a successful listing |
| `/sys/firmware/dmi` missing entirely | **no SMBIOS on this platform** — say that, do NOT say "no BMC" | F21 |
| `/sys/class/ipmi` ENOENT **AND** no `ipmi*` in `/proc/modules` **AND** no `ipmidev` in `/proc/devices` **AND** `entries` listed OK with no `38-*` | **no in-band BMC path** (the only sound "absent") | conjunction of successful negatives |
| any of the above four probes returns EACCES/EPERM/timeout | **`unknown` + which probe failed + errno** | TIMEOUT ≠ false, EACCES ≠ absent |

Extra nuance worth encoding: **`ipmi_si` not being loaded does not prove no BMC** — it may
merely be blacklisted or not yet autoloaded, and `si_tryacpi`/`si_trydmi` can be turned off
by module parameter (F8). Therefore the *firmware* evidence (DMI type 38, F18) is the more
robust presence signal than the *driver* evidence, and the sensor should report them as two
separate facts rather than collapsing them. On the target they agree; a host where DMI says
type 38 but no `ipmi_si` is loaded is the interesting "capability present, driver not
attached" state — and reporting that distinction is exactly what "absence must be proven"
means here.

## CONTRADICTIONS

**C1 — "A missing utility means no BMC capability."**
Side A (implicit in most operational tooling and in Debian #866574's user experience):
`ipmitool` failing ⇒ no IPMI. Side B (this stream): on the target, `ipmitool`, FreeIPMI and
ipmiutil are ALL absent, yet the BMC is present, IPMI 2.0, and the kernel is actively
talking to it over KCS (F5, F6). **Resolution: Side B, decisively.** Utility presence and
capability presence are independent. Recorded because the contradiction is the whole point
of the check.

**C2 — What errno does a denied `/dev/ipmi0` produce, EACCES or ENOENT?**
Side A: ipmitool prints "No such file or directory" (ENOENT) — S4-13 `open.c:115-116`,
S4-15. Side B: the kernel returns EACCES for a 0600 root-owned node opened by uid 1000.
**Resolution: both are true and that is the bug.** The syscall returns EACCES; ipmitool
*reports* ENOENT because it overwrites `errno` with two subsequent failing `open()` calls
on paths that do not exist (F13). Not contested as fact — contested as *reporting*. Our
sensor must report the syscall truth, per-path.

**C3 — Is the unprivileged sysfs BMC read cheap or expensive?**
Side A (naive, and the reason this is worth recording): it is a file in sysfs, therefore an
instant read of a cached string. Side B (F7): each `*_show` calls `bmc_get_device_id()`
which can issue a live KCS transaction. **Resolution: Side B**, with the mitigation that
the kernel caches within a validity window and serialises in-flight fetches, so the cost is
bounded by kernel IPMI timeouts (F14) rather than unbounded. Consequence: apply a timeout
to the sysfs read anyway. I did not empirically measure a first-read latency on the target
(no host access from this stream) — see GAPS.

**C4 — Does `ipmi_si` absence prove BMC absence?**
Side A: common sensor heuristic — no `ipmi_si` in `lsmod` ⇒ report "no BMC". Side B (F8,
F22): `si_tryacpi`/`si_trydmi`/`si_tryplatform` are module params that can suppress
discovery, the module may be blacklisted, and autoload may simply not have happened.
**Resolution: Side B.** Driver state and firmware declaration are two separate facts and
must be reported separately.

## STOLEN_PATTERNS

**P1 — Multi-path device probe with PER-PATH errno retention (invert ipmitool's bug).**
Source: `ipmitool/ipmitool` @ `master` `src/plugins/open/open.c:102-118`.
The path list is worth stealing verbatim as a *stat* set — `/dev/ipmi0`, `/dev/ipmi/0`,
`/dev/ipmidev/0` — because it encodes real historical layout variation (devfs-era names)
that we would otherwise miss. The control flow is worth stealing *inverted*: ipmitool
overwrites `errno` on each retry and reports only the last, turning EACCES into ENOENT.
How we apply it: `lstat` each candidate, store `(path, err)` for **every** candidate, and
resolve with explicit precedence — any `EACCES` anywhere outranks every `ENOENT` when
composing the finding; a successful `stat` outranks both. Never `open()` at all (F12, F14).

**P2 — Directory-name-as-evidence for root-only data.**
Source: `torvalds/linux` @ `v6.8` `drivers/firmware/dmi-sysfs.c:607-608`
(`kobject_init_and_add(..., "%d-%d", dh->type, entry->instance)`) + `:11-14` header comment,
with `fs/sysfs/dir.c:59` (`kernfs_create_dir_ns(..., 0755, ...)`) proving the dir is
listable. How we apply it: a generic helper that extracts structured facts from *names* in
a 0755 directory whose *contents* are 0400. Immediately reusable beyond IPMI — the same
trick works for any `type-instance` DMI structure. This converts a root-only data source
into an unprivileged presence oracle.

**P3 — Kernel-as-proxy-prober: treat a driver-populated attribute as proof of a completed
transaction we are not allowed to perform.**
Source: `ipmi_msghandler.c:2941-2946` (`guid` attribute visible only when `guid_set`) +
`:2528` `send_get_device_id_cmd`. How we apply it: the presence of `guid` in the bmc
attribute group means the kernel successfully completed Get Device GUID over KCS. We report
"in-band BMC reachable (observed indirectly via kernel-populated sysfs)" with that as
evidence — an honest, well-typed claim we could not otherwise make unprivileged, and it
also correctly avoids claiming *we* can reach the BMC.

**P4 — Conditional-visibility awareness: distinguish "attribute hidden" from "read failed".**
Source: `ipmi_msghandler.c:2927-2948` `bmc_dev_attr_is_visible`. How we apply it: maintain
the known-conditional set (`aux_firmware_revision`, `guid`) so their ENOENT maps to "BMC
did not report this field", while ENOENT on the eight unconditional attributes maps to
"unexpected — kernel/driver version differs" and is worth an `unknown`, not a `pass`.
Prevents both over- and under-claiming from the same syscall result.

**P5 — Spec-sourced enum tables instead of hand-rolled strings.**
Source: DSP0134 v3.8.0 §7.39.1 Table 115 (`01h` KCS / `02h` SMIC / `03h` BT / `04h` SSIF)
and §7.43.1 Table 124 (`40h` Network Host Interface); cross-checked against the kernel's own
`ipmi_si_intf.c:74` `si_to_str[] = { "invalid", "kcs", "smic", "bt", NULL }`. How we apply
it: if we ever render an interface-type code, use the spec table with attribution (F19
confirms DMTF permits reproduction with attribution) — and prefer echoing the kernel's
string verbatim over decoding the byte ourselves.

**P6 — Timeout justified by the governing spec, not by taste.**
Source: IPMI v2.0 rev 1.1 §9.20 KCS Driver Design Recommendations (verbatim quote in F16).
How we apply it: cite it in NOTES.md next to the per-check timeout, so the bounded-execution
invariant reads as spec conformance rather than defensive padding.
