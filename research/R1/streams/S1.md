# R1 / Stream S1 — Machine identity & hardware inventory, unprivileged

Scope: stable host id, DMI/SMBIOS (vendor/model/serial/UUID), machine-id, CPU
topology, memory, block devices (NVMe/dm/md/LVM/multipath), mounts/filesystems.
Constraints assumed: uid 1000, no sudo, read-only, static CGO_ENABLED=0
linux/amd64, no network, bounded subprocesses, permissive licenses only.

LOCAL_REPRO environment (all `LOCAL_REPRO` lines below were produced here):
- `wsl -e bash -lc 'id'` -> `uid=1000(kldrm) gid=1000(kldrm) groups=1000(kldrm),4(adm),24(cdrom),27(sudo),...`
- `uname -a` -> `Linux DESKTOP-7HHORM6 6.18.33.2-microsoft-standard-WSL2 #1 SMP PREEMPT_DYNAMIC Thu Jun 18 21:54:43 UTC 2026 x86_64 GNU/Linux`
- `/etc/os-release` -> `Ubuntu 26.04 LTS (Resolute Raccoon)`, VERSION_ID="26.04"
- CAVEAT: WSL2 is a Hyper-V VM with a Microsoft kernel, NOT bare metal. It has
  **no DMI subsystem at all** (see F5), so it can prove "code must tolerate
  absent DMI" but cannot prove the 0400 mode of DMI attrs on bare metal. The
  mode claims are therefore backed by kernel source (primary) instead.

## FACTS

### Kernel ground truth (permissions)

**F1** | The Linux kernel hardcodes mode **0400 (root-only)** for the identity-bearing
DMI attributes `product_serial`, `product_uuid`, `board_serial`, `chassis_serial`,
while every other `/sys/class/dmi/id/*` attribute is **0444 (world-readable)**:
`bios_vendor`, `bios_version`, `bios_date`, `bios_release`, `ec_firmware_release`,
`sys_vendor`, `product_name`, `product_version`, `product_sku`, `product_family`,
`board_vendor`, `board_name`, `board_version`, `board_asset_tag`, `chassis_vendor`,
`chassis_type`, `chassis_version`, `chassis_asset_tag`.
| VERIFIED | 0.98 |
evidence: https://raw.githubusercontent.com/torvalds/linux/v6.8/drivers/firmware/dmi-id.c
`drivers/firmware/dmi-id.c:41-62` at tag `v6.8` — `DEFINE_DMI_ATTR_WITH_SHOW(product_serial, 0400, DMI_PRODUCT_SERIAL)` (:49),
`(product_uuid, 0400, ...)` (:50), `(board_serial, 0400, ...)` (:56),
`(chassis_serial, 0400, ...)` (:61); contrast `(sys_vendor, 0444, ...)` (:44),
`(product_name, 0444, ...)` (:47), `(board_name, 0444, ...)` (:54).
Second source: LOCAL_REPRO-adjacent host snapshot semantics + F2 (independent code path also 0400).
| design impact: the sensor MUST treat serial/UUID as *expected* EACCES at uid 1000 and
emit UNKNOWN with `reason=EACCES`, never `fail`; vendor/model/board_name ARE readable
unprivileged and should be the primary identity fields.

**F2** | The raw SMBIOS byte tables `/sys/firmware/dmi/tables/DMI` and
`/sys/firmware/dmi/tables/smbios_entry_point` are also **0400 root-only**
(`S_IRUSR`), so the "parse SMBIOS yourself" route is closed to uid 1000.
| VERIFIED | 0.97 |
evidence: https://raw.githubusercontent.com/torvalds/linux/v6.8/drivers/firmware/dmi_scan.c
`drivers/firmware/dmi_scan.c:757-758` at `v6.8`:
`static BIN_ATTR(smbios_entry_point, S_IRUSR, raw_table_read, NULL, 0);` /
`static BIN_ATTR(DMI, S_IRUSR, raw_table_read, NULL, 0);`
Second source: `Documentation/ABI/testing/sysfs-firmware-dmi-tables` (v6.8) documents these
two files as "an alternative to utilities reading them from /dev/mem" — i.e. same
privilege class as /dev/mem.
| design impact: do NOT plan an SMBIOS parser; there is no unprivileged byte source for it.

**F3** | The per-entry DMI sysfs interface `/sys/firmware/dmi/entries/*/raw` is likewise
0400, and the kernel comments the intent explicitly: "DMI stuff is only ever admin visible".
| VERIFIED | 0.95 |
evidence: https://raw.githubusercontent.com/torvalds/linux/v6.8/drivers/firmware/dmi-sysfs.c
`drivers/firmware/dmi-sysfs.c:59`, `:76` (`.attr = {.name = __stringify(_name), .mode = 0400}`),
`:104` (comment `/* DMI stuff is only ever admin visible */`), `:449`
(`raw_event_log`, mode 0400), `:556` (`raw`, mode 0400).
| design impact: confirms F2 is a deliberate kernel policy, not an accident — the UNKNOWN
for serial/UUID is a *permanent* property of unprivileged posture sensing, worth stating in NOTES.

**F4** | `/dev/mem` (the legacy dmidecode path) is `crw-r----- root:kmem`, i.e. unreadable
by uid 1000 even before `CONFIG_STRICT_DEVMEM`/lockdown considerations.
| VERIFIED | 0.95 |
evidence: LOCAL_REPRO `wsl -e bash -lc 'ls -l /dev/mem'` ->
`crw-r----- 1 root kmem 1, 1 Sep  9 01:37 /dev/mem`; plus F2's kernel ABI doc naming
/dev/mem as the privileged alternative.
| design impact: any tool whose only SMBIOS source is /dev/mem (dmidecode) is unusable; do not exec it.

**F5** | WSL2 has **no DMI subsystem whatsoever**: `/sys/class/dmi/id/` and
`/sys/firmware/dmi/tables/` do not exist (ENOENT, not EACCES).
| VERIFIED | 0.99 |
evidence: LOCAL_REPRO on Ubuntu 26.04 / kernel 6.18.33.2-microsoft-standard-WSL2:
`ls -l /sys/class/dmi/id/` -> `ls: cannot access '/sys/class/dmi/id/': No such file or directory`;
`ls -l /sys/firmware/dmi/tables/` -> same ENOENT.
| design impact: the sensor must distinguish ENOENT (no DMI on this platform -> UNKNOWN
"platform has no SMBIOS") from EACCES (DMI present but restricted -> UNKNOWN "root-only");
these are different findings and the schema `reason` must carry the errno.

**F6** | `/etc/machine-id` is `-r--r--r-- root:root` (0444) and therefore a **fully
unprivileged, stable host identifier**; `/var/lib/dbus/machine-id` is a symlink to it.
| VERIFIED | 0.95 |
evidence: LOCAL_REPRO `ls -l /etc/machine-id` -> `-r--r--r-- 1 root root 33 Jul  7 11:52 /etc/machine-id`
(content read successfully as uid 1000; value redacted here);
`ls -l /var/lib/dbus/machine-id` -> `lrwxrwxrwx ... -> /etc/machine-id`.
Second source: systemd machine-id(5) documents mode 0444 and the dbus symlink
(https://www.freedesktop.org/software/systemd/man/machine-id.html).
| design impact: use `/etc/machine-id` as the PRIMARY stable host id (with
`/var/lib/dbus/machine-id` fallback), NOT DMI product_uuid. Note machine-id is a
local secret-ish value per systemd docs — hash it or report presence+length rather than raw value.

## CONTRADICTIONS

- **C-1 (the headline one) — ghw: "No root privileges needed for discovery" vs its own
  permission-denied warnings.**
  Side A (claim), ghw README line 14 and 16-18, verbatim: "* No root privileges needed for
  discovery" / "`ghw` goes the extra mile to be useful without root privileges. We query for
  ... to programs like `dmidecode` that require root privileges to execute."
  Side B (admission), same README lines 1045-1051 / 1135-1141 / 1197-1203, verbatim: "Some of
  the values such as serial numbers are shown as unknown because the Linux kernel by default
  disallows access to those fields if you're not running as root. They will be populated if it
  runs as root or otherwise you may see warnings like the following:" followed by
  "WARNING: Unable to read chassis_serial: open /sys/class/dmi/id/chassis_serial: permission denied",
  "WARNING: Unable to read board_serial: open /sys/class/dmi/id/board_serial: permission denied",
  "WARNING: Unable to read product_serial: open /sys/class/dmi/id/product_serial: permission denied".
  Side B is also confirmed in code (F7) and by the kernel (F1). RESOLUTION: both are literally
  true — ghw needs no root to *run*, but the identity fields we care about are empty at uid 1000.
  For our purposes the marketing headline is misleading and the *typed* result is what matters.
  Source: https://raw.githubusercontent.com/jaypipes/ghw/main/README.md (lines 14-24, 1045-1054,
  1135-1144, 1197-1206, 1294-1302).

- **C-2 — "shows unknown" vs "returns an error": three libraries, three different behaviours
  for the same EACCES.** ghw returns the string `"unknown"` and warns (F7,
  `pkg/linuxdmi/dmi_linux.go:34-37`); prometheus/procfs leaves a `*string` **nil** with an
  explicit `os.IsPermission` branch (F13, `sysfs/class_dmi.go:74-79`); go-smbios returns a
  real Go `error` (F15, `smbios/stream_linux.go:48-51`). osquery returns an **empty string**
  (F18, `system_info.cpp:107`). All four are "correct" for their own contracts; only the
  procfs/go-smbios shapes are compatible with a schema that demands a `reason`.

- **C-3 — "ghw does not shell out" vs `GHW_DISABLE_TOOLS`.** README lines 16-18 say ghw avoids
  shellouts "to programs like `dmidecode`"; but `pkg/option/option.go:27` defines
  `envKeyDisableTools = "GHW_DISABLE_TOOLS"` and `:152` `func WithDisableTools() Option`,
  which only makes sense if *some* code path executes external tools. I did not enumerate
  which paths those are (see GAPS) — so treat "no shellout" as true for the DMI path only.

- **C-4 — osquery `disk_encryption` unprivileged: zero rows, not an error.** The table
  returns an empty `QueryData` when `getuid() || geteuid()` is non-zero
  (`disk_encryption.cpp:111-114`). A consumer cannot distinguish "not root" from "no encrypted
  volumes". This directly contradicts any claim that osquery's posture answers are
  privilege-agnostic, and is the strongest external example of the failure mode our
  evidence-semantics rules forbid.

- **C-5 — `blkid` exit code vs reality.** LOCAL_REPRO: as uid 1000, `blkid` produced **no
  output** and did not report an error, because `/dev/sd*` is `brw-rw---- root:disk` (F25).
  "Successful command, empty result" is a false negative. Any design that treats a
  zero-exit-status subprocess as authoritative is wrong here.

## VERDICT_INPUT

- **github.com/jaypipes/ghw** -> **REJECT** (as evidence layer) / STEAL_PATTERN (for its
  `WithChroot`/`WithPathOverrides` seam and its `linuxdmi.Available` capability gate).
  Reason: at uid 1000 it converts EACCES into the untyped string `"unknown"` with no errno
  (F7), its memory path scrapes `/var/log/syslog` and silently substitutes usable-for-installed
  RAM (F29) — unusable for a `reason`-bearing schema — plus Windows/macOS deps (F8) and an
  unaudited external-tool path (C-3).
- **github.com/shirou/gopsutil/v4** -> **STEAL_PATTERN** (not REUSE).
  Reason: BSD-3-Clause and CGO-free on Linux, and its host-id ladder (F10) and udev-db serial
  route (F12) are exactly right, but `HostID()` returning `("", nil)` on total failure (F10)
  is the under-claiming bug our contract forbids; the useful part is ~40 lines.
- **github.com/prometheus/procfs** -> **REUSE (candidate) / STEAL_PATTERN (minimum)**.
  Reason: Apache-2.0, 3 well-known deps, and it is the only library that already models DMI
  as pointer-or-nil with an explicit `os.IsPermission` branch and regular-files-only reads
  (F13); still needs a wrapper to record *which* errno produced the nil.
- **github.com/zcalusic/sysinfo** -> **REJECT**. Reason: README states superuser is required
  for SMBIOS/DMI and RAM properties, and the shipped example `log.Fatal`s as non-root (F14).
- **github.com/u-root/u-root/pkg/smbios** -> **REJECT (for this sensor)**. Reason: all three
  of its acquisition paths (dmi tables 0400, efi systab 0400, /dev/mem) are root-only
  (F16, F2, F4) — correct code, unreachable data.
- **github.com/digitalocean/go-smbios** -> **REJECT (for this sensor)**. Reason: same
  root-only data sources (F15); its only transferable value is the honest error return (C-2).
- **osquery (tables as prior art)** -> **STEAL_PATTERN** (patterns only; never a dependency).
  Reason: `Apache-2.0 OR GPL-2.0-only` so pattern reuse is clean (F17), `/proc/meminfo`,
  `sysconf(_SC_PHYS_PAGES)`, `statfs`, `/proc/mdstat` are good unprivileged routes (F18,F20,F22),
  but its SMBIOS-backed tables and root-gated `disk_encryption`/`block_devices` are exactly
  the anti-patterns to avoid (F19,F21,C-4). It is also a C++ daemon with libcryptsetup/libudev
  linkage -> CGO, which breaks our static build.
- **util-linux `lsblk` / `lscpu` (exec)** -> **REJECT as a runtime dependency /
  STEAL_PATTERN as a map of sysfs**. Reason: everything lsblk reports unprivileged comes from
  sysfs + the udev db (F23,F24) which we can read directly; exec-ing adds an unbounded
  subprocess, version-dependent JSON, and `lscpu --json`'s awkward field/data shape (F26).
- **`dmidecode` / `lshw` / `inxi` / `facter` / `ohai` (exec)** -> **REJECT**. Reason:
  GPL-family licensing, root requirements, and absence from the target image (F27,F28);
  `facter`/`ohai` are additionally Ruby-runtime agents (not evaluated at source level — see GAPS).
- **BUILD (stdlib sysfs/procfs readers behind a test-injectable fs root)** -> **BUILD, and it
  is the only option that satisfies the contract.** Reason: every unprivileged datum we need
  (F6,F12,F24,F26,F30,F31,F32) is a bounded read of a world-readable regular file; the
  privileged data (F1,F2,F3,F16) is unavailable to *every* option, so no library can beat
  BUILD on coverage — only on typed-reason quality, where BUILD wins.

## STOLEN_PATTERNS

1. **Pointer-or-nil field with an explicit `os.IsPermission` branch, regular-files-only.**
   Source: `prometheus/procfs` @ v0.22.0, `sysfs/class_dmi.go:29-51` (all `*string`, each with
   its sysfs path in a trailing comment), `:64` (`if !f.Type().IsRegular() { continue }`),
   `:69` (skip `modalias`/`uevent`), `:74-81` (EACCES -> `continue`, other errors -> return).
   Apply: our DMI/identity reader gets exactly this shape, extended so the EACCES branch
   *records* `errno=EACCES, path=...` into the finding's evidence instead of silently skipping.
   The regular-files-only guard also satisfies our "never open device nodes/FIFOs" invariant.

2. **Capability gate before the checks, not a hostname/vendor gate.**
   Source: `ghw` `pkg/linuxdmi/dmi_linux.go:22-26` — `func Available(ctx) bool { fi, err :=
   os.Stat(filepath.Join(paths.SysClassDMI, "id")); return err == nil && fi.IsDir() }`.
   Apply: `dmiAvailable()` gates the whole DMI check family; on WSL2/containers it is false
   (F5,F32) and we emit UNKNOWN "platform exposes no DMI" rather than a pile of EACCES noise.
   This is the generic-by-design gate CLAUDE.md requires.

3. **Graceful-degradation ladder with per-rung provenance.**
   Source: `gopsutil` @ v4.26.8, `host/host_linux.go:33-63` (product_uuid -> machine-id ->
   boot_id, each rung commented with why it exists).
   Apply: same ladder for `host_id`, but the finding must name which rung answered and its
   stability class (`dmi-uuid` = hardware-stable / `machine-id` = install-stable /
   `boot_id` = per-boot). Fix gopsutil's bug: never return `("", nil)`.

4. **udev database as the unprivileged device-identity source.**
   Source: `gopsutil` @ v4.26.8, `disk/disk_linux.go:604-606` (`/run/udev/data/b<maj>:<min>`),
   `:630` (`E:ID_SERIAL`), `:656-664` (`E:ID_FS_LABEL`); corroborated by lsblk's behaviour (F24).
   Apply: read `/run/udev/data/b$(major):$(minor)` for `E:ID_MODEL`, `E:ID_SERIAL`,
   `E:ID_SERIAL_SHORT`, `E:ID_FS_TYPE`, `E:ID_FS_UUID`, `E:ID_FS_LABEL`. Cap the read; treat
   the file as a possibly-stale cache; per-key UNKNOWN when absent.

5. **sysfs-only block topology walk (no device-node open, no blkid).**
   Source: `util-linux` lsblk @ v2.40, `misc-utils/lsblk.c:414` (`ro`), `:432`
   (`queue/scheduler`), `:459` (`dm/uuid`), `:484` (`md/level`), `:491` (`device/type`),
   `:752-764` (`sysfs_blkdev_is_removable`, `sysfs_blkdev_get_parent`).
   Apply: enumerate `/sys/block/*`, then per device read `size`, `ro`, `removable`, `dev`,
   `queue/rotational`, `queue/logical_block_size`, `dm/name`, `dm/uuid`, `md/level`,
   `md/raid_disks`, plus `slaves/`+`holders/` to reconstruct dm/LVM/md/multipath stacking —
   all 0444. Never open `/dev/*` (F25).

6. **`sysconf(_SC_PHYS_PAGES) * sysconf(_SC_PAGESIZE)` for usable RAM without parsing.**
   Source: `osquery` @ 5.23.1, `osquery/tables/system/linux/system_info.cpp:52-59`.
   Apply: a cheap cross-check against `/proc/meminfo:MemTotal`; a mismatch is itself evidence.
   Pair with the memory-block count (F30) for *installed* RAM.

7. **Socket/core/thread counting from sysfs topology instead of /proc/cpuinfo heuristics.**
   Source: `gopsutil` @ v4.26.8, `cpu/cpu_linux.go:150` (`topology/core_id`), `:464-468`
   (`core_cpus_list` preferred, `thread_siblings_list` deprecated fallback) — and the
   anti-pattern to avoid: `osquery` `system_info.cpp:86-94` computes
   `cpu_sockets = logical_cores / siblings`, which breaks on heterogeneous or partially
   offline CPUs. Apply: sockets = |distinct `physical_package_id`|, physical cores =
   |distinct (package_id, core_id)|, threads = |`cpu[0-9]*`| (F26).
