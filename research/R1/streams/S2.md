# R1 / Stream S2 — Effective remote-access policy, determined WITHOUT root

Scope: what is actually in force on a running Linux host regarding who may connect, by what
authentication, as whom, over which listeners (including non-SSH paths) — restricted to what an
unprivileged (uid 1000), read-only, single-shot, no-network Go sensor can establish. Prior art
classified build-vs-buy.

Pinned artefacts used:
- openssh-portable tag `V_9_6_P1` (upstream base of the host's OpenSSH 9.6p1 Ubuntu-3ubuntu13.19)
- osquery tag `5.23.1` (latest release, published 2026-06-24)
- CISOfy/lynis tag `3.1.7` (latest release, published 2026-06-25)
- wazuh/wazuh tag `v4.14.7` (latest release, published 2026-07-30)
- jtesta/ssh-audit tag `v3.9.0` (latest release, published 2026-07-04)
- ComplianceAsCode/content tag `v0.1.82` (latest release, published 2026-09-01)

LOCAL_REPRO environment (all commands read-only; nothing installed, started, or modified):
WSL2 Ubuntu 26.04 LTS "Resolute Raccoon", kernel `6.18.33.2-microsoft-standard-WSL2`,
`uid=1000(kldrm) gid=1000 groups=1000,4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),100(users)`.
Caveat that limits several facts: this box has NO openssh-server installed
(`sshd: command not found`, `/usr/sbin/sshd: No such file or directory`), so every claim
requiring a live `sshd` binary is marked LIKELY and listed under GAPS as an
OBSERVATION_REQUEST for the Lava host, never as VERIFIED.

## FACTS

### A. OpenSSH: why `sshd -T` needs privilege, and the unprivileged way out

**F1 | `sshd -T` dies before printing anything because it loads *private* host keys first | VERIFIED | 0.97**
Evidence: openssh-portable @ `V_9_6_P1`, `sshd.c`. `main()` runs the host-key load loop at
`sshd.c:1831-1936`, calling `sshkey_load_private_type()` per `options.host_key_files[i]`
(`sshd.c:1854-1857`), and then at `sshd.c:1933-1936`:
```
	if (!sensitive_data.have_ssh2_key) {
		logit("sshd: no hostkeys available -- exiting.");
		exit(1);
	}
```
The `-T` dump is only reached *afterwards*, at `sshd.c:2000-2001`
(`if (test_flag > 1) print_config(ssh, connection_info);`); `-T` sets `test_flag = 2`
(`sshd.c:1675-1677`). The cause is documented in `sshd.8:172-177`: the default host key files
"are normally not readable by anyone but root". Independently corroborated by the host ground
truth in the brief: as uid 1000, `sshd -T` fails with exactly `no hostkeys available -- exiting`.
Design impact: `sshd -T` is structurally unavailable to us. No check may depend on it.

**F2 | OpenSSH 9.6p1 has `sshd -G`, whose config dump happens BEFORE any host-key load — this is our unprivileged path to effective sshd policy | LIKELY | 0.85**
Evidence: `sshd.c:1593-1594` — getopt string is
`"C:E:b:c:f:g:h:k:o:p:u:46DGQRTdeiqrtV"` (contains `G`); `sshd.c:1619-1620`
`case 'G': do_dump_cfg = 1; break;`; `sshd.c:1815-1816`
`if (do_dump_cfg) print_config(ssh, connection_info);`. That call site precedes the privsep-user
lookup (`sshd.c:1818-1828`) and the host-key load loop (`sshd.c:1831`). `sshd.c:1709` also exempts
`do_dump_cfg` from the absolute-path/re-exec requirement. Man page `sshd.8:157-165`:
"-G  Parse and print configuration file. Check the validity of the configuration file, output the
effective configuration to stdout and then exit."
Why LIKELY and not VERIFIED: the source ordering is proven, but I could not execute it (no local
sshd, must not install). Residual risks to settle on the host: (a) uid-1000 readability of
`/etc/ssh/sshd_config` and of every file matched by its `Include` glob; (b) whether any directive
present fatals during *parse* for non-root. Note also that `-G` is NOT announced in the OpenSSH
9.4 release notes (checked, S2-5), so its introduction release is unpinned — irrelevant to us
since we verified its presence at the exact tag we care about.
Design impact: if confirmed, `sshd -G` hands us OpenSSH's own precedence engine, and the answer is
`sshd`'s own rather than our re-derivation. Must still be a bounded subprocess (timeout + output
cap) with a fallback to our own parser plus `unknown`. **Highest-value observation request in this
stream.**

**F3 | `sshd -G -C user=...` FATALS at 9.6p1 despite the man page permitting it — unprivileged, our ceiling is the GLOBAL effective config, not Match evaluation | VERIFIED (source) / CONTESTED (vs man page) | 0.9**
Evidence: `sshd.c:1741-1747`:
```
	/*
	 * If we're not doing an extended test do not silently ignore connection
	 * test params.
	 */
	if (test_flag < 2 && connection_info != NULL)
		fatal("Config test connection parameter (-C) provided without "
		    "test mode (-T)");
```
`-C` sets `connection_info` (`sshd.c:1678-1683`); `-G` sets only `do_dump_cfg`, leaving
`test_flag == 0`, and the guard has no `do_dump_cfg` exemption. This contradicts `sshd.8:157-165`,
which says of `-G`: "Optionally, Match rules may be applied by specifying the connection
parameters using one or more -C options." Recorded as C1.
Design impact: any keyword a Match block can override must be reported as conditional/contested,
never as a single unqualified truth.

**F4 | OpenSSH is FIRST-match-wins, implemented as "assign only if still at the unset sentinel" | VERIFIED | 0.95**
Evidence: `servconf.c` @ `V_9_6_P1`. Sentinels in `initialize_server_options()`:
`servconf.c:108` `options->permit_root_login = PERMIT_NOT_SET;`,
`servconf.c:139` `options->password_authentication = -1;`.
Assignment guards in `process_server_config_line_depth()`:
`servconf.c:1404`, `:1464`, `:1595`, `:1654` (`if (*activep && *intptr == -1)`) and
`servconf.c:1485`, `:1506`, `:1555`, `:2317`, `:2394`, `:2407`, `:2499`
(`if (*activep && *charptr == NULL)`). Defaults are materialised only afterwards, in
`fill_default_server_options()` (`servconf.c:313-314`, `:365-366`). Corroborated independently by
CIS text embedded in Wazuh's policy (F23).
Design impact: hand-rolling precedence means modelling per-keyword "first assignment wins" with an
explicit unset sentinel, plus per-keyword exceptions where values accumulate or override instead
(`HostKey`, `Port`, `Subsystem` — see `servconf.c:1919` "Subsystem '%s' already defined." and
`servconf.c:2680` `debug_f("override \"%s\"", dst->subsystem_name[j])`). This is exactly where a
naive sensor silently becomes wrong, and it is the strongest argument for F2.

**F5 | `Include` is expanded INLINE at its line, glob-ordered, non-fatal on no-match, and cannot clobber the container's Match state — so Ubuntu's line-1 Include makes drop-ins WIN | VERIFIED | 0.93**
Evidence: `servconf.c:2128-2215` (`case sInclude:`):
- rejected on the command line — `:2129-2132` `fatal("Include directive not supported as a command-line option")`
- relative paths rooted at `SSHDIR` — `:2142-2145`
- container Match state saved/restored around each include — `:2151` `oactive = *activep;`, restored at `:2167` and `:2212`
- glob expansion — `:2177` `glob(arg, 0, NULL, &gbuf)`; `GLOB_NOMATCH` is explicitly NOT fatal, a placeholder cache entry is recorded instead (`:2178-2192`)
- each matched file is loaded and parsed immediately, in glob order — `:2195-2213` (`load_server_config` then `parse_server_config_depth(..., depth + 1)`)
Design impact (load-bearing for the Lava host): `sshd_config` line 1 is
`Include /etc/ssh/sshd_config.d/*.conf`, so the drop-in `00-latitude-instant-deploy.conf` is
parsed *before* the body of `sshd_config`. With F4 (first wins), **the drop-in beats the main file
for every keyword it sets**. A sensor that reads `/etc/ssh/sshd_config` top-to-bottom and ignores
includes can report the exact opposite of what is in force. Also: `glob(3)` sorts by default, so
the `NN-` numeric prefix convention is semantically load-bearing and we must sort identically if
we enumerate drop-ins ourselves. And a missing drop-in directory is *legal*, not an error — so
"no drop-ins found" must not be reported as a failure.

**F6 | Match blocks are a TWO-PASS, per-connection overlay — global-only parsing cannot resolve them, by design | VERIFIED | 0.93**
Evidence: `servconf.c:995-1007`, verbatim design comment:
"The strategy for the Match blocks is that the config file is parsed twice. The first time is at
startup. activep is initialized to 1 and the directives in the global context are processed and
acted on. Hitting a Match directive unsets activep and the directives inside the block are checked
for syntax only. The second time is after a connection has been established but before
authentication. activep is initialized to 2 and global config directives are ignored since they
have already been processed..."
Mechanics at `servconf.c:1354-1364`: when `*activep == 0` and the keyword lacks `SSHCFG_MATCH`, it
either fatals ("Directive '%s' is not allowed within a Match block") or, in connection mode,
silently skips it as "a directive we have already processed".
Design impact: a finding for e.g. `PasswordAuthentication` must be shaped as
`{global_effective_value, match_blocks_present, keywords_overridden_in_match:[...]}`. A bare
boolean, when a Match block touches that keyword, is over-claiming.

**F7 | Upstream 9.6p1 defaults: `PermitRootLogin prohibit-password`, `PasswordAuthentication yes` — so "absent from config" is NOT "disabled" | VERIFIED | 0.95**
Evidence: `servconf.c:313-314`
`if (options->permit_root_login == PERMIT_NOT_SET) options->permit_root_login = PERMIT_NO_PASSWD;`
and `servconf.c:365-366`
`if (options->password_authentication == -1) options->password_authentication = 1;`.
Design impact: the compiled-in default set is a property of the *binary*, unreadable from `/etc`.
Therefore never emit `pass` for "password auth is off" merely because the keyword is absent.
Either we hold `sshd -G` output as evidence, or the finding is `unknown` with reason
`default_not_observable`. This is the concrete instance of the project rule "do NOT report
'default' as 'in force' without evidence".

**F8 | Debian/Ubuntu override upstream defaults via drop-ins, not by editing sshd_config | LIKELY | 0.7**
Evidence: host ground truth in the brief (drop-in `00-latitude-instant-deploy.conf` present;
observed `PasswordAuthentication no`, `PermitRootLogin prohibit-password`); Ubuntu cloud images
conventionally place `50-cloud-init.conf` under `/etc/ssh/sshd_config.d/`. Packaging-level primary
source not obtained inside the time box (see GAPS).
Design impact: *provenance* is part of the evidence. Report which `file:line` set each effective
value, not just the value. Reusable shape:
`{keyword, effective_value, source_file, source_line, source_kind: main|dropin|default|match}`.
`sshd -G` gives the value but not the provenance — which is why our own Include-aware parse is
still needed even if F2 confirms (see VERDICT_INPUT).

### B. Socket activation — "the listener" is not the daemon

**F9 | Ubuntu switched sshd to systemd socket activation in openssh `1:9.0p1-1ubuntu1` (22.10), and on 24.04 the socket's port/address are derived from `sshd_config` by a systemd GENERATOR | LIKELY | 0.7**
Evidence: Ubuntu changelog for `openssh_9.6p1-3ubuntu13`
(`https://changelogs.ubuntu.com/changelogs/pool/main/o/openssh/openssh_9.6p1-3ubuntu13/changelog`)
records the introduction of `debian/patches/systemd-socket-activation.patch` and
`debian/systemd/ssh.socket` / `ssh.service` at `1:9.0p1-1ubuntu1`, to use socket activation by
default. Ubuntu's own announcement thread
(`https://discourse.ubuntu.com/t/sshd-now-uses-socket-based-activation-ubuntu-22-10-and-later/30189`)
states the change applies to 22.10, 23.04, 23.10 and 24.04 LTS, and that in 24.04 port/address
settings "are no longer migrated, but the port and address settings are pulled dynamically from
`sshd_config` via a systemd generator" (earlier releases migrated them into
`/etc/systemd/system/ssh.socket.d/addresses.conf`).
Marked LIKELY: the changelog stanza was read through a summarising fetch rather than quoted
verbatim, and Debian's actual `debian/ssh.socket` unit text could not be retrieved
(`sources.debian.org` and `salsa.debian.org` paths tried returned 404). So `ListenStream=22`,
`Accept=no`, `FreeBind=yes` are reported by secondary sources only — treat as SPECULATIVE until
the unit file on the host is read directly.
Design impact, and it is significant: on Ubuntu 24.04 the *actual* listening addresses may come
from a generator's reading of `sshd_config`, not from a static unit. So the truthful evidence
chain for "which addresses accept SSH" is: `sshd_config` `Port`/`ListenAddress` →
generator output under `/run/systemd/generator*/` → `ssh.socket` `ListenStream` → observed
socket in `/proc/net/tcp`. All four links are world-readable and none needs root. A sensor that
reports only the last link cannot explain a mismatch; one that reports only the first is guessing.

**F10 | Under `Accept=no`, the listening fd is handed to the spawned service — so the owner of the :22 listener legitimately differs before vs. after the first connection | LIKELY | 0.6**
Evidence: `systemd.socket(5)`, `Accept=` (Ubuntu Noble manpages mirror,
`https://manpages.ubuntu.com/manpages/noble/man5/systemd.socket.5.html`; canonical
freedesktop.org page returned HTTP 403): with `Accept=no` (the default) "all listening sockets
themselves are passed to the started service unit, and only one service unit is spawned for all
connections"; with `Accept=yes` systemd retains the listening socket and passes only accepted
connection sockets. The consequence — that before any activation the listener is attributable to
pid 1 and after activation to the sshd process — is an inference from these semantics, not a
directly sourced statement, hence 0.6. It needs empirical confirmation on the host
(`ss -ltnp | grep :22` and `/proc/net/tcp` before vs. after a connection).
Design impact: **process attribution of the SSH listener is not stable over time**, independently
of privilege. Even as root, "which pid owns :22" answers differently at different moments on the
same correctly-configured host. Our check must therefore be phrased about the *path* (is a
socket-activated or daemon-owned SSH listener configured and live) rather than about a pid.

**F11 | Unprivileged, `ss -ltnp` omits the Process column silently — exit status 0, header present, data missing | VERIFIED (LOCAL_REPRO + mechanism per F13) | 0.92**
Evidence LOCAL_REPRO (WSL2 Ubuntu 26.04, kernel 6.18.33.2-microsoft-standard-WSL2, uid 1000):
`ss -ltnp` printed the `Process` header, but the field was EMPTY for every row (listeners owned by
uid 989 and uid 0 — systemd-resolved stub resolvers). The same run under `ss -ltn` produced
identical address data. Reproduced twice, once by me and once by a parallel worker in the same
environment. Mechanism corroborated by osquery's implementation (F14) and by `proc_pid_fd(5)` (F13).
Note: the man page text for `ss(8)` retrieved from man7.org documents only
"-p, --processes: Show processes using sockets" and states no privilege caveat, so the limitation
is undocumented there — behavioural, not documented. iproute2 source line numbers not obtained.
Design impact: **`ss -ltnp` degrades by omission, not by error.** A sensor that trusts its exit
code reports "nothing listening / no process" as a PASS. This is the archetypal silent-false in
this domain. Any socket-to-process claim must be gated on "did we actually read that pid's fd
directory", and be `unknown` otherwise.

**F12 | `/proc/net/tcp` and `/proc/net/tcp6` ARE fully readable unprivileged and DO expose the owning uid and socket inode for every socket, including other users' | VERIFIED (LOCAL_REPRO + kernel docs) | 0.9**
Evidence LOCAL_REPRO, header and rows read as uid 1000:
```
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  timeout inode
   0: 3500007F:0035 00000000:0000 0A 00000000:00000000 00:00000000 00000000   989        0 4833 ...
   1: FEFFFF0A:0035 00000000:0000 0A 00000000:00000000 00:00000000 00000000     0        0 5134 ...
```
The `uid` column is populated (989, 0) for sockets we do not own; `st` `0A` is TCP_LISTEN;
`local_address` is hex `ADDR:PORT`. Field layout and semantics confirmed against
`https://docs.kernel.org/networking/proc_net_tcp.html` — `uid` is "the ID of the user that owns
the socket", and `inode` is "a number that identifies the socket to the Linux virtual filesystem".
Design impact: this is our primary listener-enumeration primitive — a stdlib file read, no exec,
no network, cheap and deterministic. We CAN verify "a socket is in LISTEN on 0.0.0.0:22 and its
owner is uid 0". We CANNOT verify "that socket belongs to sshd". Those are two findings with
different confidence, never one over-claiming finding.

**F13 | inode→pid resolution is gated by a ptrace access-mode check, not merely by file mode — so it is limited to our own uid regardless of directory permissions | VERIFIED | 0.85**
Evidence: `proc_pid_fd(5)` (`https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html`):
"Permission to dereference or read (readlink(2)) the symbolic links in this directory is governed
by a ptrace access mode PTRACE_MODE_READ_FSCREDS check". LOCAL_REPRO: `ls -ld /proc/1/fd` →
`dr-x------ 2 root root`, and `ls -l /proc/1/fd` as uid 1000 → `Permission denied`, while
`ls -l /proc/self/fd` succeeded (`lr-x------ 1 kldrm kldrm 64 ... 0 -> pipe:[21117]`).
Design impact: the reason code must be `ptrace_scope_denied` / `proc_fd_unreadable`, not
"file not found". And it means the limitation cannot be engineered around by any permission tweak
we are allowed to make (we are allowed none) — it is a hard ceiling, so the corresponding finding
is permanently `unknown` on this host class and should be documented as such rather than
re-attempted per run.

**F14 | Unprivileged users CAN query systemd unit state and enumerate socket units — this is our attribution fallback | VERIFIED (LOCAL_REPRO) | 0.8**
Evidence LOCAL_REPRO as uid 1000: `systemctl is-active ssh.socket` returned `inactive` with no
permission error; `systemctl show ssh.socket` returned `LoadState=not-found` (this box has no
openssh-server); `systemctl list-units --type=socket` and
`systemctl list-unit-files --type=socket` both succeeded, enumerating ~19 socket units with
LOAD/ACTIVE/SUB state (e.g. `snapd.socket`, `dbus.socket`). Read-only D-Bus property reads need
no privilege.
Design impact: since socket→pid attribution is impossible (F13) and listener ownership is unstable
(F10), the *only* sound way to attribute :22 to SSH unprivileged is the declarative layer:
world-readable unit files plus unprivileged unit-state queries. Concretely:
(a) `listener_present` on :22 from `/proc/net/tcp` — PASS/FAIL, high confidence;
(b) `listener_owner_process` — `unknown`, reason `proc_fd_unreadable`;
(c) `ssh_activation_path` — read `ssh.socket`/`ssh.service` unit files from the world-readable
search path and, as a bounded exec fallback, `systemctl is-active`/`show -p ListenStream`.
Corollary trap: a socket-activated sshd is spawned per connection, so "is sshd running" via a
process scan can be legitimately FALSE while SSH is fully available. A sensor that checks for an
`sshd` process (as Lynis SSH-7402 does, F19) reports "no SSH daemon" on a correctly configured
Ubuntu 24.04 host that is accepting SSH at that moment.

### C. Sudo / "as whom" — not answerable from files

**F15 | Effective sudo authority is NOT determinable unprivileged; group membership is a necessary-not-sufficient proxy | VERIFIED (LOCAL_REPRO, matches host) | 0.93**
Evidence LOCAL_REPRO: `/etc/sudoers` is `-r--r----- 1 root root 1800` (0440) → unreadable by
uid 1000; `/etc/sudoers.d/README` is `-r--r----- 1 root root 863`. Divergence worth recording:
WSL's `/etc/sudoers.d` is `drwxr-xr-x` (listable, contents unreadable) whereas the Lava host's is
0750 (not even listable). Lynis independently classifies the equivalent check as root-only
(F20: AUTH-9252 registered `--root-only YES`).
Design impact: emit `unknown` for "who may escalate", with the specific path and errno as evidence,
and separately emit a *distinct* observation: "login user is a member of group `sudo` (evidence:
getgroups / `/etc/group` line)". Never merge them: group membership does not prove a sudoers rule
grants anything, and a sudoers rule can grant authority to a user in no privileged group at all.
The two hosts differ in whether `/etc/sudoers.d` can even be *listed*, so the reason vocabulary
must distinguish `dir_unlistable` from `file_unreadable` (see C3).

### D. Prior art at source level

**F16 | osquery `ssh_configs` never reads `sshd_config` at all, and has no `Include` support — it is a *client*-config table | VERIFIED | 0.95**
Evidence: osquery @ `5.23.1`, `osquery/tables/system/ssh_configs.cpp`:
`:30-31` `kUserSshConfig = ".ssh/config"`, `kSystemwideSshConfig = "/etc/ssh/ssh_config"`;
`:91-95` selects the Windows or POSIX system-wide *client* file; `:82-89` iterates users reading
`<home>/.ssh/config`. The parser at `:50-66` lowercases each line, treats `host `/`match ` prefixes
as an opaque `block` string, and emits the remaining raw line as `option`. The token `include`
does not occur anywhere in the file. No precedence, no defaults, no `sshd_config`, no Match
evaluation.
Design impact: osquery is REJECT as a source of effective *server* policy. Its row shape
(`uid, block, option, ssh_config_file`) is nonetheless a good *raw evidence* shape to retain
beside our resolved value.

**F17 | osquery's socket→process mapping is /proc/pid/fd walking, and unprivileged gaps are hidden behind a magic `-1` plus a debug log | VERIFIED | 0.93**
Evidence: `osquery/tables/networking/listening_ports.cpp:25`
`auto sockets = SQL::selectAllFrom("process_open_sockets");` — `listening_ports` is a pure
derivation and inherits every limitation of `process_open_sockets`.
`osquery/tables/networking/linux/process_open_sockets.cpp`:
`:47-49` "under /proc/<pid>/fd and search for links of the type socket:[<inode>]. Extract the inode
and fd (filename) and index it by inode number";
`:74-77` on failure it only logs `VLOG(1) << "Results for process_open_sockets might be
incomplete. Failed to acquire socket inode to process map for pid "`;
`:103-128` per-namespace `procGetSocketList(AF_INET / AF_INET6 / AF_UNIX / AF_PACKET, ...)`;
`:143-156` the correlation step:
```
    auto proc_it = inode_proc_map.find(info.socket);
    if (proc_it != inode_proc_map.end()) {
      r["pid"] = proc_it->second.pid;
      r["fd"] = proc_it->second.fd;
    } else if (!pid_filter) {
      r["pid"] = "-1";
      r["fd"] = "-1";
```
Design impact: STEAL the two-phase architecture (build inode→pid map, then correlate against the
per-namespace socket list) — it is correct. REJECT the failure semantics: `pid = -1` plus a VLOG is
exactly the "silently incomplete" pattern our contract forbids. Ours must be an explicit per-socket
`attribution: unknown` with `reason: proc_fd_unreadable`, plus a scan-level count of how many pids
were and were not resolvable, so a reviewer can see the coverage.

**F18 | osquery `sudoers` DOES follow all four include spellings — worth copying as an enumeration duty even though we cannot read the targets | VERIFIED | 0.9**
Evidence: `osquery/tables/system/posix/sudoers.cpp:85-87`:
```
    // We frequently check if these are include headers. Do it once here.
    auto is_include = (header == "#include" || header == "@include");
    auto is_includedir = (header == "#includedir" || header == "@includedir");
```
plus `:90` (a `#`-leading line is only a comment if it is *not* an include), `:100-106` (include
with an empty target handled explicitly), `:107` (line-continuation `\` deliberately not honoured
for include lines), `:118-134` (includedir listing, with `TLOG << "Could not list includedir: "`
at `:127` and a sudoers(5)-quoting comment at `:134`).
Design impact: STEAL_PATTERN — the four spellings and the "`#` is not always a comment" subtlety.
Even unprivileged, we should *enumerate* the include graph we would need and report each
unreadable node with its own path and errno; that is far better evidence than one aggregate
"sudoers unreadable".

**F19 | Lynis derives ALL sshd values from one cached `sshd -T -C user=doesnotexist,...` run — the `-C` synthetic identity is a genuinely good idea, but the whole approach requires root | VERIFIED | 0.95**
Evidence: lynis @ `3.1.7`, `include/tests_ssh`, `:45-53` inside SSH-7402:
```
        if IsRunning "sshd"; then
            OPENSSHD_RUNNING=1
            ...
            CreateTempFile
            SSH_DAEMON_OPTIONS_FILE="${TEMP_FILE}"
            # Use a non-existing user, to ensure that systems that have a Match block configured, will be evaluated as well
            ${SSHDBINARY} -T -C user=doesnotexist,host=none,addr=none 2> /dev/null > ${SSH_DAEMON_OPTIONS_FILE}
```
`:118` SSH-7408's own note: "Instead of parsing the configuration file, we query the SSH daemon
itself"; `:119-120` gates SSH-7408 on `-n "${SSH_DAEMON_OPTIONS_FILE}"` and OpenSSH >= 5.1;
`:186` value extraction
`awk -v OPT="${OPTIONNAME_LOWER}" 'index($0, OPT) == 1 { print toupper($2) }' ... | tail -1`;
`:123-145` the expectation grammar `<OptionName>:<Expected>,<Medium>,<Weak>:<TestType>` with test
types `=`, `<`, `>`, `!` (documented at `:127-130`); `:301`, `:312` the AllowUsers/AllowGroups
greps.
Two fragilities to avoid: `2> /dev/null` discards precisely the stderr that explains the failure
(our `no hostkeys available` case), and `index($0, OPT) == 1` is a prefix match, so
`clientalive` would also match `clientalivecountmax`.
Design impact: STEAL the `-C` synthetic-identity idea as the right way to surface Match-conditional
overrides (though F3 blocks us from using it with `-G`); REJECT `2> /dev/null`; REJECT prefix
matching — `sshd -G/-T` output is `key value`, so split on first whitespace and compare whole keys.

**F20 | Lynis's privilege degradation is a declarative per-test flag with a structured skip-reason taxonomy — steal the taxonomy, reject the behaviour | VERIFIED | 0.93**

**C1 — `sshd -G` with `-C`: man page vs source (OpenSSH `V_9_6_P1`). Both sides recorded.**
- Side A, `sshd.8:157-165`: "-G  Parse and print configuration file. … Optionally, Match rules may
  be applied by specifying the connection parameters using one or more -C options."
- Side B, `sshd.c:1741-1747`: `if (test_flag < 2 && connection_info != NULL) fatal("Config test
  connection parameter (-C) provided without test mode (-T)");` — `-G` leaves `test_flag == 0` and
  there is no `do_dump_cfg` exemption, so `-G -C` fatals.
- Resolution: code governs behaviour; the man page is aspirational or stale at this tag. Report as
  CONTESTED, verify empirically (OR-2), and build nothing that depends on `-G -C` working.

**C2 — "osquery is GPLv2" (task premise) vs osquery's LICENSE. Both sides recorded.**
- Side A, task premise: osquery is GPLv2, therefore a licensing blocker.
- Side B, `LICENSE` @ 5.23.1: `SPDX-License-Identifier: Apache-2.0 OR GPL-2.0-only`, with "If
  you're using osquery you are free to choose one of the provided licenses."
- Resolution: dual-licensed, Apache-2.0 electable → not a licensing blocker. Rejected on capability
  grounds instead (F16, F17).

**C3 — `/etc/sudoers.d` observability differs across hosts. Both sides recorded.**
- Lava host: `/etc/sudoers.d` is 0750 → cannot even list it.
- LOCAL_REPRO (WSL Ubuntu 26.04): `/etc/sudoers.d` is 0755 → can list, cannot read contents.
- Resolution: both are real and neither is wrong. Same final status (`unknown`), different evidence
  and different errno stage, so the reason vocabulary must distinguish `dir_unlistable` (EACCES on
  opendir) from `file_unreadable` (EACCES on open). A genericity requirement, not a host quirk.

**C4 — "Is the SSH daemon running?" has two defensible answers under socket activation. Both sides recorded.**
- Process view (`lynis include/tests_ssh:45` `IsRunning "sshd"`): can be legitimately FALSE on a
  socket-activated host between connections.
- Listener/unit view (`/proc/net/tcp`, `ssh.socket` active): TRUE.
- Resolution: report both as separate findings with separate evidence; never let one imply the
  other. On the Lava host both happen to be true (`ssh.service` active running `sshd -D` AND
  `ssh.socket` listening) — which is precisely the configuration that would hide this bug from us
  if we only ever tested there. A genericity trap, and an argument for a fixture-based test with a
  socket-only host.

**C5 — Who owns the listening :22 fd under `Accept=no`. Both sides recorded, unresolved.**
- Side A: systemd (pid 1) creates and holds the listening socket, so attribution points at pid 1.
- Side B (`systemd.socket(5)`, `Accept=` per S2-23): with `Accept=no` "all listening sockets
  themselves are passed to the started service unit", so once activated the fd is held by sshd.
- Resolution: both are true at different times — pid 1 before first activation, the service after.
  Confidence 0.6, needs OR-4/OR-5. Consequence for design: never build a check that asserts a
  specific owning pid for :22; assert on the configured activation path instead (F14).

## STOLEN_PATTERNS

1. **Declarative privilege/prerequisite metadata on the check registration.**
   Source: `lynis 3.1.7 include/functions:2643-2650` (`--root-only` parsing) and `:2763-2764`
   (enforcement). Apply: each Fixed-Registry entry carries
   `requires: {root: bool, utilities: [...], paths: [...], platform: ...}`; the runner evaluates it
   *before* the check body and — unlike Lynis — still emits one finding with `status: unknown` and
   the matching reason.

2. **A closed, authored-once reason vocabulary.**
   Source: `lynis 3.1.7 include/functions:2707-2764` (nine distinct `SKIPREASON` strings). Apply:
   `unknown.reason ∈ {needs_root, file_unreadable, dir_unlistable, ptrace_scope_denied,
   utility_missing, unsupported_platform, prerequisite_missing, subject_absent, execution_error,
   timeout, output_truncated, budget_exceeded, indeterminate}`. A closed set is reviewable,
   greppable and testable; an open string field is none of those.

3. **Four-way XCCDF semantics preserved inside a three-value status.**
   Source: the XCCDF rule-result enumeration (F28). Apply:
   `notapplicable → unknown + reason:subject_absent`;
   `notchecked → unknown + reason:budget_exceeded|not_run`;
   `error → unknown + reason:execution_error|timeout`;
   `unknown → unknown + reason:indeterminate|file_unreadable|ptrace_scope_denied`.
   Document the mapping in NOTES.md so a reviewer can reconstruct the standard's distinction from
   our output.

4. **Two-phase socket attribution (map first, correlate second).**
   Source: `osquery 5.23.1 process_open_sockets.cpp:47-63` (build inode→(pid,fd) from
   `/proc/<pid>/fd`, then correlate against per-namespace socket lists) and `:143-156` (correlate).
   Apply: same two phases, but replace the `pid="-1"` sentinel (`:149-151`) with an explicit
   per-socket `attribution: unknown, reason: proc_fd_unreadable`, and record how many pids were and
   were not readable as scan-level evidence so coverage is visible.

5. **Include-graph enumeration with all four spellings.**
   Source: `osquery 5.23.1 sudoers.cpp:85-87` (`#include`, `@include`, `#includedir`,
   `@includedir`), `:90` (`#` is not always a comment), `:118-134` (includedir listing with an
   explicit "Could not list includedir" branch at `:127`). Apply: for both sudoers and sshd_config,
   walk the include graph and report every unreadable node with its own path and errno, rather than
   one aggregate failure.

6. **Multi-location config discovery with a contested-duplicate signal.**
   Source: `lynis 3.1.7 include/tests_ssh:24` (candidate directory list
   `/etc /etc/ssh /usr/local/etc/ssh /opt/csw/etc/ssh /usr/etc/ssh`) and `:70-90` (readability test
   at `:78-84`, `ReportException "${TEST_NO}:01"` at `:75` when a *second* candidate exists, and
   "SSH daemon is running, but no readable configuration file found" at `:90`). Apply: search a
   candidate list for genericity, and when two candidate configs are both present emit a
   `contested` finding instead of silently preferring one — matching our "contradiction ≠ first
   observation wins" rule.

7. **Query the subject; don't re-derive it — but keep provenance.**
   Source: `lynis 3.1.7 include/tests_ssh:118` ("Instead of parsing the configuration file, we
   query the SSH daemon itself"). Apply: prefer `sshd -G` for the *value*, and our own Include-aware
   parse for the *provenance* (`file:line`, `source_kind`). Emitting both lets each validate the
   other, and a mismatch is itself a high-value finding.

8. **Composable (source, extractor, matcher) rule triple plus compliance mapping.**
   Source: `wazuh v4.14.7 cis_ubuntu24-04.yml:50-54` (`condition:` plus `f:`/`d:`/`c:` sources

   typed Go structs rather than a string DSL — and make "the command failed" a first-class outcome,

9. **Declared-vs-observed listener reconciliation.**
   Source: composition of `systemd.socket(5)` `Accept=` semantics (S2-23),

10. **Public-half host key inventory as a no-network substitute for wire observation.**
