FACT: util-linux `lsblk(8)` "reads the sysfs filesystem and udev db to gather information" and only falls back to direct LABEL/UUID/fstype probing "if the udev db is not available or lsblk is compiled without udev support"; blkid(8) is called out as "the authoritative information about filesystems and raids" [S7]. This is the citable reason lsblk -J can print SERIAL/WWN/FSTYPE (sourced from /run/udev/data/b<maj>:<min>, populated by udev's blkid-calling rules at hotplug/boot time, i.e. read historically, not live) while a live `dd if=/dev/sda` by the sensor's own unprivileged process gets EACCES — lsblk is consuming udev's cached probe, not re-probing the device itself.
STATUS: VERIFIED (man page text quoted) — the specific "columns go empty when unreadable" phrasing was NOT found verbatim in the page fetched; inferred from the udev-db-fallback structure (GAP: exact empty-column wording).
APPLIES_TO: both
PROBE: `lsblk -J -O` (or targeted `-o NAME,SERIAL,WWN,FSTYPE`) always succeeds for an unprivileged caller when udev db entries exist; empty string for a column means either udev never populated that key (device never blkid-probed, e.g. truly empty partition) or the running lsblk had no udev support — sensor cannot distinguish these two from lsblk output alone; do not treat empty FSTYPE as proof of "no filesystem" without corroboration (e.g. also checking /sys/block/<dev>/<part>/... size != 0 and absence of a partition table another way).
IMPACT: Prefer lsblk over raw device reads for descriptive metadata (matches "stdlib → native OS primitive" design rule); treat empty lsblk fields as UNKNOWN-not-FALSE unless corroborated.

FACT: RFC 7468 defines the generic PEM textual encoding: encapsulation boundaries "-----BEGIN <label>-----" / "-----END <label>-----" (exactly 5 hyphens each side, one space before the label, base64 body per RFC 4648 §4, 64-char line wrap) with standard labels including CERTIFICATE, PRIVATE KEY, ENCRYPTED PRIVATE KEY, PUBLIC KEY, X509 CRL, CERTIFICATE REQUEST [S11]. OpenSSH's own private-key container (PROTOCOL.key, openssh-portable tag V_9_6_P1) begins with the literal ASCII magic string `"openssh-key-v1"` followed by a NUL byte, wrapped by ssh-keygen in the conventional armor `-----BEGIN OPENSSH PRIVATE KEY-----` / `-----END OPENSSH PRIVATE KEY-----` (armor lines are the widely-used de facto convention around the RFC7468-style envelope; PROTOCOL.key itself documents only the inner binary magic, not the armor text) [S12].
STATUS: VERIFIED (RFC text quoted directly; PROTOCOL.key magic string quoted directly; armor-line pairing is well-established convention, not re-quoted from a second primary in this pass — LIKELY for that specific sub-claim)
APPLIES_TO: generic
PROBE: bounded ≤64-byte read of file start, classify-then-discard: match literal byte prefix `-----BEGIN ` for RFC7468 PEM family (branch further on the label word), or match `"openssh-key-v1\0"` for OpenSSH's binary-magic-inside-PEM-armor. JKS: first 4 bytes big-endian == 0xFEEDFEED; JCEKS: 0xCECECECE (from OpenJDK JavaKeyStore.java `MAGIC` / JceKeyStore.java `JCEKS_MAGIC` constants, confirmed via search snippets of hg.openjdk.org sources — not independently byte-fetched this pass) [S13]. MIT Kerberos keytab: first byte always 5 (0x05), second byte = format version (1 or 2) — i.e. magic bytes `0x05 0x02` for the common v2/big-endian keytab format, per MIT krb5 "Keytab file format" doc [S14].
IMPACT: A single ≤64-byte bounded read per candidate file (never opened for more, never logged as content) is sufficient to classify PEM/OpenSSH-key/JKS/JCEKS/keytab shapes for a "secret-shaped file present" finding; the byte pattern is the evidence, the file content is discarded immediately after classification — satisfies the "no secret values" invariant.

FACT: /proc/[pid]/mountinfo has exactly the fields the lead already pinned (docs.kernel.org / proc(5) family): (1) mount ID, (2) parent ID, (3) major:minor, (4) root, (5) mount point, (6) mount options, (7) zero-or-more optional fields "tag[:value]" (shared/master/propagate_from/unbindable), (8) a literal single-hyphen separator marking end-of-optional-fields, (9) filesystem type, (10) mount source, (11) super options [S19]. Confirmed via `man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html` (note: the generic `proc.5.html` page does NOT contain this table — it only cross-references `proc_pid_mountinfo(5)` as a separate page; fetching the wrong page silently gives nothing, a documentation-navigation trap worth flagging to whoever else touches this).
STATUS: VERIFIED
APPLIES_TO: generic
PROBE: parse by splitting on the literal `" - "` (space-hyphen-space) token, NOT by fixed field count — field 7 is variable-length (0..N optional tag tokens) so any fixed-offset/fixed-split-count parser silently misparses fields 9-11 whenever optional tags are present (common with shared-subtree mounts, e.g. containers/systemd). This is the #1 parsing trap per the prompt's own framing and is corroborated by the man page's explicit callout that parsers must skip unrecognized optional-field tags.
IMPACT: Sensor's mount-table parser must locate the `" - "` separator token first, then parse fields 9-11 relative to it, and fields 1-6 plus variable-count optional fields relative to the start — never assume a fixed column count.
