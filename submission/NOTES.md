# NOTES — Lava sensor exercise

**What was built.** `sensor scan --out findings.json`: a static Go binary that describes the machine and runs 26 read-only, bounded, unprivileged checks in five categories — `REMOTE_ACCESS`, `SECRETS_ON_DISK`, `BMC_INBAND_ACCESS` (required) plus `STORAGE_POSTURE` and `BOOT_CHAIN`. Every registered check emits exactly one finding per run; a check that cannot establish its answer says `unknown` with the errno, exit code, timeout or budget that stopped it.

**Assumptions.** The host has no Go toolchain, so the tarball ships a cross-compiled linux/amd64 binary plus source and the `go build` line. The sensor never opens device nodes, never runs `sudo`, never issues IPMI commands (the BMC is read through sysfs only) and makes no network calls. `host_id` is a keyed hash of `/etc/machine-id`; `owner` is an explicit `unknown` with the candidates the machine exposes, because every owner-bearing source here is root-only or an OEM placeholder. Severity is the check's declared impact for `fail` and `unknown` (an unverifiable control is an equal assurance gap) and `info` for `pass`.

**Ambiguities.** (1) `finding.schema.json` was named as supplied but not in the material I received; rather than ask, the contract embedded in the brief was transcribed into the shipped `finding.schema.json` (draft 2020-12, provenance file included) and validation runs against it. (2) `cores` = physical cores; logical CPUs, sockets and threads are extra fields. Unknown numerics are `0` only together with a `machine.unknowns` entry naming the reason; strings use the literal `unknown`. (3) "Actually in force" for sshd: `sshd -G` (unprivileged here) gives the effective configuration; a second check compares config mtimes with the daemon's start time and says `unknown` inside the clock's resolution. (4) A denied read is never a finding of absence: EACCES, timeouts and missing utilities stay `unknown`, and only a directory the account cannot traverse counts as protection from that account.

**Custom categories.** `STORAGE_POSTURE` — data at rest and hand-back hygiene on rented hardware: no dm-crypt/LUKS, the root on one NVMe while an identical unpartitioned 960 GB drive sits attached (never opened), drive health `unknown` by proof (SMART needs CAP_SYS_ADMIN). `BOOT_CHAIN` — the brief's example, kept because the most severe fact on this host lives there: Secure Boot disabled in Setup Mode, lockdown `none`, an unsigned out-of-tree `bnxt_en` module loaded, a newer kernel installed than running.

**Verification.** Independent Claude reviewers in fresh contexts that had not written the code were told to make the sensor lie; every round found real defects (the last: a permission model that counted a file's owner as a member of its own group, turning `/etc/sudoers` 0440 root:root into a false `fail`). Each defect has a closure-table row with a regression test or an explicit justification, and a hostile Docker profile (eleven utilities removed, key directories mode 0000, an unmapped uid) is a mechanical gate.

**With another day.** Verify the provider's sudoers/image policy and the `module_blacklist=` origin; run on real RHEL-family and Alpine machines, not only containers; evaluate `sshd -G -C` for Match-conditional policy; cut the roster to the ~15 checks with the most evidence per line.

**One thing Claude got wrong that I rejected.** The architecture challenger ranked a *capability-gated* registry first: a pre-phase that probes paths, utilities and permissions and gates checks behind them. The host showed why that is wrong: AppArmor's `profiles` file is mode 0444 yet returns EACCES, so capability can only be established by the read attempt itself — the pre-phase would have reported the wrong thing, at ~250 extra lines and a single point of failure. The shipped design keeps the flat fixed registry and moves the guarantee into one engine rule: any `pass`/`fail` resting on a non-OK observation is downgraded to `unknown` by the engine, not by the author's discipline.
