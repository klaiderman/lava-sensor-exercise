# NOTES — Lava sensor exercise

**What was built.** `sensor scan --out findings.json`: a static Go binary that describes the machine and runs 26 read-only, bounded, unprivileged checks in five categories — `REMOTE_ACCESS`, `SECRETS_ON_DISK`, `BMC_INBAND_ACCESS` (required) plus `STORAGE_POSTURE` and `BOOT_CHAIN`. Every registered check emits exactly one finding per run; a check that cannot establish its answer says `unknown` with the errno, exit code, timeout or budget that stopped it. On your server the final run took under 100 ms: 12 pass, 10 fail, 4 unknown; the shipped `findings.json` is that run, hash-verified against the shipped binary.

**Assumptions.** The host has no Go toolchain, so the tarball ships a cross-compiled linux/amd64 binary plus source and the `go build` line. The sensor never opens device nodes, never runs `sudo`, never issues IPMI commands (BMC facts come from sysfs) and makes no network calls. `host_id` is a keyed hash of `/etc/machine-id`; `owner` is an explicit `unknown` with the candidates the machine exposes, because every owner-bearing source here is root-only or an OEM placeholder. Severity is the check's declared impact for `fail` and `unknown`, `info` for `pass`.

**Ambiguities.** (1) `finding.schema.json` was named as supplied but not in the material I received; rather than ask, the contract embedded in the brief was transcribed into the shipped `finding.schema.json` (draft 2020-12, provenance file included) and validation runs against it. (2) `cores` = physical cores, with logical CPUs, sockets and threads as extra fields; unknown numerics are `0` only with a `machine.unknowns` entry naming the reason. (3) "Actually in force" for sshd: `sshd -G` gives the effective configuration; a second check compares config mtimes with the daemon start time and says `unknown` inside the clock resolution. (4) A denied read is never a finding of absence: EACCES, timeouts and missing utilities stay `unknown`; only a directory the account cannot traverse counts as protection from that account.

**Custom categories.** `STORAGE_POSTURE` — data at rest and hand-back hygiene on rented hardware: no dm-crypt/LUKS, the root on one NVMe while an identical unpartitioned 960 GB drive sits attached (never opened), drive health `unknown` by proof (SMART needs CAP_SYS_ADMIN). `BOOT_CHAIN` — the brief's example, kept because the most severe fact on this host lives there: Secure Boot disabled in Setup Mode, lockdown `none`, an unsigned out-of-tree `bnxt_en` module, a newer kernel installed than running.

**Verification and known limitations.** Four independent Claude reviewers in fresh contexts that had not written the code were told to make the sensor lie; every round found real defects (one: the owner counted as a member of its own group, turning `/etc/sudoers` 0440 root:root into a false `fail`). Each fixed defect has a closure-table row with a regression test, and a hostile Docker profile (eleven utilities removed, key directories mode 0000, an unmapped uid) is a mechanical gate. **Three High findings from the fourth review are not fixed.** None applies to your server or to stock Ubuntu/RHEL/Alpine, but each yields a false verdict elsewhere: (a) protection judgements ignore POSIX ACLs, so an ACL granting another user traverse on an owner-only directory gives a false `pass`; (b) the owner is subtracted from group membership by name, so a uid-0 alias or a NIS `+` passwd line gives a false `fail` on `/etc/sudoers`; (c) a symlinked store directory is judged by the symlink's own 0777 mode, a false `fail`. One honest under-claim remains: the BMC declaration check reports `unknown` because the SMBIOS entry attributes are root-only.

**With another day.** Fix those three classes; verify the provider's sudoers/image policy and the `module_blacklist=` origin; run on real RHEL-family and Alpine machines.

**One thing Claude got wrong that I rejected.** The architecture challenger ranked a *capability-gated* registry first: a pre-phase probing paths, utilities and permissions, gating checks behind it. The host showed why that is wrong: AppArmor's `profiles` file is mode 0444 yet returns EACCES, so capability can only be established by the read attempt itself — the pre-phase would have reported the wrong thing at ~250 extra lines and a single point of failure. The shipped design keeps the flat fixed registry and puts the guarantee in one engine rule: any `pass`/`fail` resting on a non-OK observation is downgraded to `unknown` by the engine, not by author discipline.
