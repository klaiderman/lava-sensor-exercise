# NOTES — Lava sensor exercise

**What was built.** `sensor scan --out findings.json`: a static Go binary (no runtime dependencies) that describes the machine and runs 26 read-only, bounded, unprivileged checks in five categories — `REMOTE_ACCESS`, `SECRETS_ON_DISK`, `BMC_INBAND_ACCESS` (required) plus two of my own, `STORAGE_POSTURE` and `BOOT_CHAIN`. Every registered check emits exactly one finding per run; a check that cannot establish its answer says `unknown` with the errno, exit code, timeout or budget that stopped it.

**Assumptions.** Go is the language; the host has no Go toolchain, so the tarball ships a cross-compiled linux/amd64 binary plus source and a `go build` line. The sensor never opens device nodes, never runs `sudo`, never issues IPMI commands (the BMC is identified through sysfs attributes under an out-of-band deadline), and makes no network calls. `host_id` is a keyed hash of `/etc/machine-id` (never the raw value); `owner` is an explicit `unknown` with the candidates the machine exposes (provider, facility, image host-key comment) because every owner-bearing source on this host is root-only or an OEM placeholder. Severity = the check's declared impact for `fail` and `unknown` (an unverifiable control is an assurance gap of equal weight), `info` for `pass`.

**Ambiguities and how they were settled.** (1) `finding.schema.json` was named as supplied but was not in the material I received; rather than ask, the contract embedded in the PDF/HTML was cross-checked (identical) and transcribed into `finding.schema.json` (draft 2020-12, provenance file included) — validation is against that transcription. (2) "cores": physical cores, with logical CPUs/sockets/threads as extra fields. (3) Unknown numerics: `0` only together with a `machine.unknowns` entry naming the reason and sources tried; strings use the literal `unknown`. (4) "Actually in force" for sshd: `sshd -G` (which works unprivileged on this host) gives the effective on-disk configuration; a separate check compares config mtimes with the daemon's start time and says `unknown` when the two fall inside the clock's resolution — the sensor does not pretend to read the running daemon's memory.

**Custom categories and why.** `STORAGE_POSTURE` — data at rest and decommissioning hygiene on rented hardware: this machine has no dm-crypt/LUKS anywhere, its root sits on a single NVMe while an identical, unpartitioned 960 GB drive is attached and never opened by the sensor, and drive health is `unknown` *by proof* (SMART needs CAP_SYS_ADMIN). Lava's own public writing names media sanitization and bare-metal hand-back; anything written here survives hand-back in cleartext. `BOOT_CHAIN` — the brief's own example, kept because the most severe fact on this host lives there: Secure Boot disabled with the platform in Setup Mode, kernel lockdown `none`, and an unsigned out-of-tree module (`bnxt_en`) loaded.

**With another day.** Verify the provider's sudoers/image policy and the `module_blacklist=` origin (Latitude.sh docs are gated); run the same binary on a RHEL-family and an Alpine machine for real, not only in containers; make the profile matrix and the evidence-entails-verdict property part of `go test` on every profile; evaluate `sshd -G -C` for Match-conditional policy; decode a live multi-entry ACL; reduce the sensor to the ~15 checks that carry the most evidence per line.

**One thing Claude got wrong that I rejected.** The architecture challenger ranked a *capability-gated* registry first: a pre-phase that probes capabilities (paths, utilities, permissions) and gates checks behind them. I rejected the separate gate layer. The host itself showed why: AppArmor's `profiles` file is mode 0444 yet returns EACCES, so capability can only be established by the read attempt itself — a pre-phase would have reported the wrong thing at ~250 extra lines and a single point of failure. The shipped design keeps the flat fixed registry and moves the guarantee into a central rule: any `pass`/`fail` resting on a non-OK observation is downgraded to `unknown` by the engine, not by the check author's discipline. (A second, smaller rejection: an early recon rule inferred "virtual machine" from "the command printed something"; `systemd-detect-virt` had printed `none` — parse the value, never the presence of output.)

**Transcript note.** Two native Claude Code session files are included (the session forked once); one Anthropic API-key value that a sub-agent printed into its own transcript is redacted in the staged copies (count disclosed in the transcript README). Mid-turn instructions I sent while agents were running are stored by Claude Code as queued-command attachment records rather than user turns; they are preserved in the native files but a plain user/assistant rendering will not show them as turns.
