## Direction Lock
- Intent: research the smallest production-quality Go implementation of the sensor for the task and host we now understand. Default runtime is a Fixed Registry of checks (deterministic, explicit, reviewable, bounded); no runtime LLM; no external planning/rule engine. Change the default only if evidence disproves it — and say what evidence.
- Audience: the lead, the architecture challenger (Grill-Me), the implementation author. Feeds the architecture options and the implementation prompt.
- Output format: architecture notes with cited evidence, an implementation-level build-vs-buy table, a recommended module layout, and code-level patterns (short Go snippets allowed, ≤ 30 lines each, cited to stdlib docs/source).
- Constraints: Go stdlib first; `golang.org/x/sys` only if justified; static `CGO_ENABLED=0` binary; no daemon/DB/UI/API/CI; one command runs it (`sensor scan --out findings.json`); testable without weakening production behaviour (test-only seams, not a production "override root" flag).

## Questions to answer
1. Module layout for a ~2–4k LOC sensor: `cmd/sensor`, `internal/{machine,checks,evidence,runner,exec,fsread,output,schema}` or better — justify with prior art in well-run Go CLIs (e.g. node_exporter collectors, osquery-like table registries in Go, `ghw`, Cloudflare/Google tooling). How do mature projects register collectors/checks statically and keep them isolated?
2. Bounded execution: the correct Go pattern for `exec.CommandContext` + process-group kill (`Setpgid`, `Cancel`, `WaitDelay`), avoiding pipe hangs when grandchildren hold stdout, capping output (`io.LimitReader` + kill on overflow), per-check deadlines with `context`, panic recovery per check (`recover()` → unknown finding), total scan deadline, goroutine leaks. Cite `os/exec` docs/source and known issues (golang/go issues on WaitDelay/pipes).
3. Safe file reading: `/proc` and `/sys` files with size 0/4096, `os.ReadFile` vs bounded reader, `O_NOFOLLOW`/`Lstat` policy (sysfs symlinks are legitimate; user-writable paths are not), never opening char/block devices or FIFOs (check `Mode()` first), reading directories without following into mounts (`xdev` semantics in Go: compare `Dev` from `Stat_t`), bounded directory walks (`filepath.WalkDir` with depth/entry/time caps and skip lists), reading POSIX ACLs via `unix.Getxattr("system.posix_acl_access")` vs exec `getfacl` — is x/sys justified for this and for `Statfs`/`Stat_t` fields?
4. Evidence model in Go: typed evidence (source path/command, observed value, errno/exit code/timeout/truncation), an `Observation` result type distinguishing OK/EACCES/ENOENT/UNSUPPORTED/TIMEOUT/UTILITY_MISSING/EXEC_ERROR, how a check turns observations into pass/fail/unknown with reasons; how to keep evidence JSON stable and deterministic (struct ordering, sorted maps, `json.Encoder` with `SetEscapeHTML(false)`, no floats where ints suffice).
5. Schema validation: which Go JSON-schema library (draft coverage 2020-12/2019-09/07, dependency footprint, maintenance) — validate at runtime before writing (embed the schema with `embed`) vs test-time only; recommendation with trade-offs given "we cannot run it = no credit" and the schema file being supplied by Lava.
6. Machine description implementation: DMI via sysfs, `/etc/machine-id`, `/proc/cpuinfo` + `/sys/devices/system/cpu` topology for physical cores, `/proc/meminfo`, `/sys/block` enumeration with NVMe/SCSI model lookup, `/etc/os-release` parsing, kernel release — with the exact unknown-handling for each field (no empty strings, no guesses).
7. CLI and packaging for the deliverable: `flag` vs a subcommand pattern in stdlib, exit codes, `--out` semantics, `--version`, optional `--timeout`, logging to stderr only; building a static linux/amd64 binary from Windows (cross-compile) and the fallback `go build` on the host (is Go present on the host? check the snapshot); the "one command" that Lava runs; the tarball layout (source + prebuilt binary + README + NOTES + findings.json + session export).
8. Testability without weakening production: fs abstraction (`fs.FS`/`os.DirFS` root injection internal to the package, test-only), runner interface for command execution with fixture-driven fakes, golden-file tests for findings JSON, fault-injection harness (EACCES via chmod in temp dirs, timeouts via `sleep` shims, malformed output fixtures, missing utilities via PATH manipulation), deterministic clock injection. What to avoid (global mutable state, init-time side effects).
9. Implementation-level build-vs-buy: for each of `procfs` parsing, DMI, block devices, JSON schema, ACLs, sshd config parsing (is there a Go OpenSSH config parser worth reusing? `golang.org/x/crypto/ssh` has none for sshd_config; `github.com/kevinburke/ssh_config` is client config) — REUSE/STEAL_PATTERN/BUILD/REJECT with evidence.
10. Answer: "What is the smallest architecture we'd be comfortable shipping onto a real customer host?" and "What fact would make us abandon the Fixed Registry default?"
